# 테스트 케이스 목록 (한글 정리)

이 문서는 `shopping-mall-harness` 쇼핑몰 사이트가 의도한 대로 동작하는지 확인하는
테스트 케이스를 사람이 읽을 수 있는 말로 정리한 것입니다. 실제로 이 케이스들을
자동으로 실행하는 코드는 `tests/e2e/*.spec.js`(Playwright)에 있으며, 이 문서는 그
코드의 요약본입니다. 함수/테스트 이름은 참고용으로만 괄호에 적어둡니다.

각 항목은 PRD(`_workspace/01_planner_prd.md`)의 요구사항 번호와 매핑되어 있어서,
어떤 요구사항이 테스트로 커버되는지 추적할 수 있습니다. 사이클별로 섹션을 나누고,
기존 항목은 지우지 않고 이어서 추가합니다.

## 3차 사이클 — 장바구니 전체 비우기 + 수량 할인

> 자동화 파일: `tests/e2e/cart.spec.js`

### 전체 비우기

(`cart.spec.js` › `장바구니 전체 비우기 (PRD 11.1~11.5, 13.2)`. 11.2는 클릭 후 나간 요청을
전부 기록해 `DELETE /api/cart` **한 건뿐**임을 확인하고, 11.4는 다이얼로그 리스너를 미리 걸어
한 번도 발화하지 않는 것을 확인한다. 11.5는 "DOM에 존재"와 "화면에 안 보임"을 각각 단언한다)

| PRD | 시나리오 |
|---|---|
| 11.1 | 장바구니 화면에 "전체 비우기" 버튼이 있다 |
| 11.2 | 버튼을 누르면 한 번의 요청으로 장바구니 전체가 비워진다 (항목을 하나씩 지우는 방식이 아니다) |
| 11.3 | 이미 비어있는 장바구니에서 비우기를 시도해도 에러가 나지 않는다 |
| 11.4 | 비우기 버튼을 눌러도 "정말 비우시겠습니까?" 같은 확인창이 뜨지 않고 바로 처리된다 |
| 11.5 | 장바구니가 비어있을 때는 비우기 버튼 자체가 화면에서 숨겨진다 |

### 수량 기반 자동 할인

(`cart.spec.js` › `수량 기반 자동 할인 (PRD 12.1~12.13, 14.2~14.5)`. 12.4는 할인 요소를
`toHaveCount(0)`으로(숨김이 아니라 부재), 함정 케이스는 9개일 때와 10개일 때의 줄 합계 문구가
**실제로 같다는 것까지 확인한 뒤** 할인 표시 요소의 존재 여부로 통과 판정을 한다)

| PRD | 시나리오 |
|---|---|
| 12.1 | 한 상품을 장바구니에 **9개** 담으면, 할인이 적용되지 않고 정가로만 표시된다 |
| 12.2 | 같은 상품을 **10개** 담으면, 그 줄 전체에 10% 할인이 자동으로 적용된다 |
| 12.3 | 할인이 적용된 줄에는 원래 가격(취소선) + 할인된 가격 + "10개 이상 담으면 10% 할인 적용" 안내 문구가 표시된다 |
| 12.4 | 할인이 적용되지 않은 줄에는 할인 관련 표시(할인가, 안내 문구)가 아예 나타나지 않는다 (흐리게 숨기는 게 아니라 화면에 존재하지 않음) |
| 12.5 | 할인 여부는 상품 줄마다 각자 독립적으로 판단된다 — 한 상품이 6개, 다른 상품이 5개면 합쳐서 11개가 되어도 어느 쪽도 할인되지 않는다 |
| 12.6 | 장바구니 전체 합계는 할인이 반영된 금액의 합이다 |
| **함정 케이스** | 9개일 때와 10개일 때 최종 줄 합계 숫자가 우연히 똑같아 보일 수 있다 (정가 × 9 = 할인가 × 10인 경우). 이런 경우에도 "금액이 맞다"가 아니라 "할인 표시(취소선·안내 문구)가 실제로 뜨는지"를 기준으로 통과 여부를 판단해야 한다 |

## 4차 사이클 — 모의 결제 (2026-08-10)

> 자동화 예정 파일: `tests/e2e/checkout.spec.js`(결제 화면), `tests/e2e/order.spec.js`(주문 확인 화면).
> 장바구니 화면의 "결제하기" 링크(15.x)는 기존 `tests/e2e/cart.spec.js`에 블록을 추가한다.
>
> **이번에 만드는 결제는 "모의 결제"입니다.** 실제 카드사·결제대행사와 연결되지 않고,
> 화면에서 고른 결제 수단 두 가지("승인 성공" / "승인 거절") 중 무엇을 골랐는지에 따라
> 서버가 그 자리에서 성공·실패를 정해서 돌려줍니다. 그래서 실패 상황을 언제든 똑같이
> 다시 만들어볼 수 있습니다.

### 장바구니 → 결제 진입 (PRD 15.x)

| PRD | 시나리오 |
|---|---|
| 15.1 | 장바구니에 담긴 상품이 있으면 "결제하기" 링크가 보이고, 누르면 결제 화면으로 이동한다 |
| 15.1 | "결제하기"는 진짜 링크라서 새 탭으로 열거나 뒤로 가기를 눌러도 브라우저 기본 동작대로 동작한다 |
| 15.2 | 장바구니가 비어 있으면 "결제하기" 링크는 화면에서 보이지 않는다 (요소 자체는 화면 구조에 남아 있고 숨겨지기만 한다 — 비우기 버튼과 같은 방식) |
| 15.5 | "결제하기" 링크가 생겨도 "장바구니 비우기" 버튼은 그대로 있고, "결제하기"를 눌렀다고 해서 장바구니가 비워지지는 않는다 |
| 15.3 | 결제 화면으로 들어가는 입구는 장바구니 화면 하나뿐이다 — 상품 목록·상품 상세·상단 공통 헤더 어디에도 결제 링크나 "바로 구매" 버튼이 없다 |

| 16.1 | 결제 화면에 들어갈 때 장바구니 정보를 서버에 딱 한 번만 물어본다 — 화면 요약과 상단 수량 배지를 그 한 번의 답변으로 함께 채운다 (같은 정보를 두 번 물어보지 않는다) |
| 16.19 | 상단 장바구니 수량 배지에 표시되는 숫자는 서버가 알려준 총 수량과 같다 |
| 16.2 | 결제 화면의 요약은 읽기 전용이다 — 수량을 올리거나 내리는 버튼, 삭제 버튼, 비우기 버튼이 없다. 내용을 바꾸려면 장바구니로 돌아가야 한다 |
| 16.3 | 결제 화면에는 장바구니로 돌아가는 링크가 있다 |
| 16.4 | 장바구니 화면에서 보던 총 금액과 결제 화면의 총 금액이 정확히 같다 (10개 이상 담아 할인이 걸린 줄이 있어도 같다) |
| 16.5 | 결제 화면에는 할인 표시(취소선 친 원래 가격·할인가·할인 안내 문구)가 나타나지 않는다 — 할인이 이미 반영된 금액만 보여준다 |

### 결제 화면 — 입력 (PRD 16.6~16.7)

| PRD | 시나리오 |
|---|---|
| 16.6 | 입력란은 주문자 이름과 연락처 두 개뿐이다 — 주소·우편번호·이메일·배송 요청사항, 그리고 카드번호·유효기간·CVC 같은 실제 결제 정보 입력란은 하나도 없다 |
| 16.7 | 결제 수단은 "모의 결제 (승인 성공)"과 "모의 결제 (승인 거절 — 실패 테스트용)" 두 개의 선택지가 전부이고, 화면에 들어오면 "승인 성공" 쪽이 미리 선택되어 있다 |
| 16.7 | 결제 수단 이름에 "모의"와 "실패 테스트용"이라는 말이 드러나 있어서, 화면을 보는 사람이 진짜 결제로 오해하지 않는다 |

### 결제 화면 — 결제 요청 (PRD 16.8~16.10)

| PRD | 시나리오 |
|---|---|
| 16.8 | "결제하기"를 누르면 서버에는 주문자 이름·연락처·결제 수단 세 가지만 전달된다 — 금액이나 상품 목록은 보내지 않는다 (결제할 내용과 금액은 서버가 스스로 장바구니에서 다시 계산한다) |
| 16.9 | "승인 거절"을 골라도 화면이 미리 실패로 처리하지 않는다 — 반드시 서버에 요청을 보내고, 서버가 거절이라고 답한 뒤에야 실패가 표시된다 (실제로 요청이 나갔는지 요청 개수로 확인한다) |
| 16.10 | 결제 버튼을 빠르게 여러 번 눌러도 결제 요청은 딱 한 번만 나간다 |
| 16.10 | 결제에 실패한 뒤에도 결제 버튼은 다시 눌릴 수 있는 상태가 된다 (실패했다고 재시도가 막히지 않는다) |

### 결제 화면 — 성공 (PRD 16.11)

| PRD | 시나리오 |
|---|---|
| 16.11 | "승인 성공"으로 결제하면 결제 화면에 머무르지 않고 곧바로 주문 확인 화면으로 이동한다 |
| 18.7 | 결제에 성공하면 장바구니가 비워진다 — 장바구니 화면으로 돌아가면 "비어 있습니다" 상태이고, 결제하기 링크도 숨겨진다 |
| 18.7 | 장바구니가 비워져도 이미 만들어진 주문의 상품 내용은 그대로 남아 있다 (주문 내역이 장바구니와 함께 지워지지 않는다) |

### 결제 화면 — 실패 갈래 (PRD 16.12~16.16, 16.20)

| PRD | 시나리오 |
|---|---|
| 16.12 | "승인 거절"로 결제하면 주문 확인 화면으로 넘어가지 않고 결제 화면에 그대로 머물면서, 서버가 보낸 안내 문구가 표시된다 |
| 16.12 | 승인이 거절되어도 입력해둔 주문자 이름과 연락처가 지워지지 않고 그대로 남아 있다 |
| 16.12 | 승인이 거절되어도 주문 요약과 총 금액이 그대로 보인다 (에러 안내가 요약을 가리지 않는다 — 다시 시도하려면 입력 폼이 보여야 하기 때문) |
| 16.12 | 승인이 거절된 뒤 결제 수단을 "승인 성공"으로 바꿔서 다시 누르면 이번에는 결제에 성공한다 |
| 16.13 | 주문자 이름을 비워두고 결제하면 화면이 이동하지 않고, "주문자 이름을 1자 이상 30자 이하로 입력해 주세요" 같은 서버 안내가 표시된다 |
| 16.14 | 장바구니가 비어버린 상태에서 결제를 시도하면 "장바구니가 비어 있어 결제할 수 없습니다" 안내와 함께 **상품 목록으로 가는 링크**가 같이 보이고, 화면은 이동하지 않는다 |
| 16.20 | 네트워크 문제로 결제 요청이 실패하면 에러 안내가 표시되고 화면이 비거나 깨지지 않는다 |
| 16.15 | 결제가 성공하지 않은 모든 경우(입력 오류·승인 거절·빈 장바구니·네트워크 오류)에 장바구니는 절대 비워지지 않는다 — 상단 수량 배지도 그대로이고, 장바구니 화면으로 돌아가면 담긴 줄·수량·총액이 결제 시도 전과 완전히 같다 |
| 16.16 | 장바구니가 빈 상태로 결제 화면에 바로 접속하면 "장바구니가 비어 있습니다" 안내와 상품 목록 링크만 보이고, 주문자 입력란·결제 수단 선택지·결제하기 버튼은 화면에 보이지 않는다 |

### 결제 화면 — 상태와 검증 규칙 (PRD 16.17~16.18)

| PRD | 시나리오 |
|---|---|
| 16.18 | 화면은 입력값을 미리 검사하지 않는다 — 이름과 연락처를 완전히 비워둔 채 결제해도 요청이 실제로 서버까지 나가고, 서버가 돌려준 안내 문구가 화면에 표시된다 |
| 16.18 | 브라우저가 자체적으로 전송을 막는 입력 검사(필수 입력 표시 등)를 쓰지 않는다 — 그래서 잘못된 입력으로 결제를 시도하는 상황을 항상 재현할 수 있다 |
| 16.17 | 장바구니 정보를 아예 불러오지 못하면(서버 오류) 요약과 입력 폼은 숨겨지고 에러 안내만 보인다 |
| 16.17 | 로딩 중·정상(요약+폼)·빈 장바구니, 이 세 가지 중 항상 하나만 보인다. 단 결제 요청이 실패했을 때의 안내는 예외로, 요약과 폼이 보이는 상태 위에 함께 표시된다 |

### 주문 확인 화면 (PRD 17.x)

| PRD | 시나리오 |
|---|---|
| 17.1 | 주문 확인 화면에는 주문번호·결제 상태·주문 일시·주문자 이름·연락처·주문한 상품 줄들·총 수량·총 금액이 모두 표시된다 |
| 17.1 | 주문번호는 `ORD-날짜8자리-영문숫자6자리` 형식이다 (예: `ORD-20260810-K3F9A2`) |
| 17.2 | "결제 완료"라는 표시는 서버가 알려준 주문 상태 값에 근거해서 나온다 — "여기까지 왔으니 성공이겠지"라고 화면이 임의로 적어넣지 않는다 |
| 17.4 | 장바구니에서 보던 총 금액, 결제 화면의 총 금액, 주문 확인 화면의 총 금액 세 개가 정확히 같다 (할인이 걸린 줄이 있어도 같다) |
| 17.5 | 주문 확인 화면을 새로고침해도 주문 정보가 그대로 표시된다 (서버에서 다시 조회하기 때문) |
| 17.6 | 주소에 주문번호가 아예 없으면 서버에 요청을 보내지 않고 바로 "주문을 찾을 수 없습니다" 상태가 된다 |
| 17.7 | 존재하지 않는 주문번호로 접속하면 "주문을 찾을 수 없습니다" 안내와 상품 목록으로 가는 링크가 표시된다 |
| 17.8 | 다른 브라우저(또는 시크릿 창)에서 같은 주문 주소를 열면 주문 내용이 보이지 않고 "주문을 찾을 수 없습니다"가 표시된다 — 주문을 만든 브라우저에서만 볼 수 있다 |
| 17.8 | "없는 주문"과 "남의 주문"은 화면상 똑같이 처리된다 — "권한이 없습니다" 같은 별도 화면을 만들지 않는다 |
| 17.9 | 주문 확인 화면에는 상품 목록으로 돌아가는 링크와 상단 공통 헤더(장바구니 링크·수량 배지)가 있다 |
| 17.10 | 결제에 성공해 장바구니가 비워졌으므로, 주문 확인 화면의 상단 수량 배지는 0이 되어 숨겨진다 |
| 17.11 | 로딩 중·정상·찾을 수 없음·에러, 이 네 가지 중 항상 하나만 보인다 |
| 17.12 | 주문 확인 화면에도 할인 표시(취소선·할인가·안내 문구)가 나타나지 않는다 — 할인이 반영된 금액만 보여준다 |
| 17.13 | 주문 확인 화면에는 주문 취소·환불 요청·재주문·영수증 출력·배송 조회 버튼이 없다 |
| 19.13 | 주문 일시는 화면에 사람이 읽기 좋은 형태로 보이되, 프로그램이 읽는 원본 시각 값도 함께 담겨 있다 (표기 방식이 바뀌어도 테스트가 깨지지 않도록 원본 값으로 확인한다) |

### 서버가 지켜야 하는 규칙 (PRD 18.x — API 단위로 확인)

| PRD | 시나리오 |
|---|---|
| 18.3 | 같은 내용으로 결제를 몇 번을 요청해도 결과가 항상 같다 — "승인 거절"을 고르면 몇 번을 눌러도 항상 거절된다 (확률이나 시간에 따라 결과가 달라지지 않는다) |
| 18.5 | 주문자 이름이 없거나, 공백만 있거나, 30자를 넘으면 결제가 거절되고 이름을 고치라는 안내가 나온다. **정확히 30자는 통과하고 31자부터 거절된다** |
| 18.5 | 연락처는 하이픈이 전부 있는 형태(`010-1234-5678`, `010-123-4567`)와 하이픈이 전혀 없는 형태(`01012345678`, `0101234567`)만 허용된다 |
| 18.5 | 하이픈이 섞인 형태(`010-12345678`), 자릿수가 모자란 형태(`010-1234-567`), 휴대폰이 아닌 번호(`02-123-4567`), 공백으로 구분한 형태(`010 1234 5678`), 글자(`abc`), 빈 값은 모두 거절된다 |
| 18.5 | 결제 수단이 정해진 두 값이 아니면(예: 대소문자가 다르거나 다른 이름이면) 거절된다 |
| 18.5 | 입력이 잘못된 채로 "승인 거절"을 골라 보내도, 승인 판정보다 입력 검사가 먼저 이루어져서 "입력을 고치라"는 안내가 나온다 |
| 18.6 | 장바구니가 비어 있는 상태로 결제를 요청하면 "장바구니가 비어 있어 결제할 수 없습니다"로 거절된다. 이는 "입력을 고치세요"와는 다른 안내다 |
| 18.4 | 승인이 거절되면 주문이 저장되지 않고 주문번호도 만들어지지 않으며, 장바구니도 그대로 남는다 |
| 18.16 | 결제에 성공한 직후 똑같은 요청을 한 번 더 보내면 이번에는 "장바구니가 비어 있다"는 이유로 거절된다 — 같은 주문이 두 번 만들어지지 않는다 |
| 18.10 | 존재하지 않는 주문번호로 조회하거나, 다른 브라우저에서 조회하거나, 식별 정보 없이 조회하는 세 경우 모두 **똑같은 응답**을 받는다 ("권한 없음"과 "없음"을 구분해서 알려주지 않는다) |
| 18.11 | 주문 목록을 한꺼번에 조회하는 기능은 만들지 않았다 |
| 8.6 | 주문 정보를 받아올 때 장바구니 식별 정보(cartId)는 응답에 들어 있지 않다 — 브라우저가 읽을 수 없어야 하는 값이기 때문 |
| 18.12 | 결제나 주문 처리 중 예기치 못한 서버 오류가 나면, "상품 목록을 불러오지 못했습니다" 같은 엉뚱한 문구가 아니라 결제·주문 상황에 맞는 문구가 나온다 (과거에 실제로 있었던 버그의 재발 방지) |
| 12.5 | 10개 이상 담아 할인이 걸린 줄이 있는 채로 결제하면, 주문에 저장된 줄에도 할인 정보가 그대로 남고 총 금액은 할인이 반영된 금액이다 |
| 18.8 | 결제해도 상품 재고는 줄지 않는다 (재고 개념 자체가 없다) |
| 18.13 | 실제 결제대행사 연동, 결제창 팝업, 웹훅, 주문 취소·환불·영수증 발급은 하나도 만들지 않았다 |

### 화면 요소가 "숨겨지는 것" vs "아예 없는 것" (PRD 19.18)

| PRD | 시나리오 |
|---|---|
| 19.18 | "결제하기" 링크는 장바구니가 비어도 화면 구조에는 남아 있고 보이지 않게만 처리된다 (비우기 버튼·수량 배지와 같은 방식) |
| 19.18 | 결제 화면과 주문 확인 화면의 상품 줄은 표시할 내용이 있을 때만 만들어진다 — 줄 개수를 세는 것만으로 몇 개가 표시됐는지 알 수 있다 (할인 표시 요소와 같은 방식) |

### 브라우저 창을 파일당 하나만 씁니다 (2026-08-09 변경)

테스트 개수와 내용은 그대로 45개입니다. 달라진 것은 **창이 몇 번 열리는가** 하나입니다.

- 예전에는 테스트 하나마다 새 브라우저 창이 열리고 닫혔습니다. `--headed`로 직접 지켜보면
  창이 45번 깜빡여서 무엇을 보고 있는지 알기 어려웠습니다.
- 이제는 **spec 파일 하나가 창 하나를 끝까지 같이 씁니다.** 파일이 3개이므로 창도 3개입니다.
  (`npx playwright test --headed --workers=1`로 확인한 실제 결과입니다.)
- 예외가 하나 있습니다. "서로 다른 브라우저는 장바구니가 서로 독립적이다"(8.5)와
  "처음 방문한 브라우저에 식별 정보가 새로 발급된다"(8.2/8.4)는 요구사항 자체가 창 여러 개를
  전제로 합니다. 이 두 케이스만 자기 창을 따로 열어 검증하고, 끝나면 바로 닫습니다.
  그래서 한 번 실행에 만들어지는 창은 총 6개입니다(공유 3 + 예외 3).

창을 같이 쓰면 장바구니(쿠키)도 같이 쓰게 되어, 앞 테스트가 담아둔 상품이 다음 테스트에
그대로 남습니다. 그래서 **각 테스트는 시작할 때 서버 장바구니를 비우고 시작합니다.**
"앞 테스트가 뭘 남겼든 상관없이 같은 결과가 나온다"는 성질은 그대로 유지하되, 그 방법만
"매번 새 창"에서 "매번 빈 장바구니"로 바꾼 것입니다. 단언을 느슨하게 만든 곳은 없습니다.

읽을 때 참고할 점 몇 가지입니다.

- 각 테스트는 빈 장바구니에서 시작하므로 장바구니가 서로 섞이지 않습니다. 화면을 가로채는
  설정(예: "이미지가 전부 실패하는 상황")도 테스트가 끝나면 원래대로 되돌립니다.
- 파일끼리는 여전히 동시에 실행되고, 서로 다른 창이라 장바구니도 서로 다릅니다.
  다만 한 파일 안에서는 적어놓은 순서대로 실행됩니다(창을 같이 쓰기 위한 조건입니다).
- 화면에 보이는 금액은 테스트가 직접 계산하지 않고, 매번 서버에 장바구니를 따로 물어봐서
  그 값과 글자 단위로 비교합니다 (7.6 규칙을 테스트도 그대로 지킵니다).
- "요청이 나가지 않아야 한다"는 케이스(6.9, 7.4, 11.2, 7.8)는 화면 모양이 아니라
  **실제로 오간 요청 개수**로 확인합니다.
- 요소가 "화면에 안 보이는 것"(비우기 버튼, 합계 영역, 수량 배지)과 "아예 없는 것"(할인 표시)은
  서로 다른 방식으로 확인합니다. 이 둘을 섞으면 할인 경계 버그를 놓칩니다.
