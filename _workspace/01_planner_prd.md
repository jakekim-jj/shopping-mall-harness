> 개정: product-planner / 2026-08-08 (2차: 상품 상세 + 장바구니 추가)
> 개정: product-planner / 2026-08-09 (3차: 장바구니 전체 비우기 + 수량 기반 자동 할인)
> 개정: product-planner / 2026-08-10 (**4차: 모의 결제 — 외부 PG 미연동**)
> 이 문서는 backend-agent, frontend-agent, qa-agent의 공통 출발점이다.
> **여기 적힌 필드명·응답 shape은 확정값이다.** 바꿔야 할 사정이 생기면 임의로 바꾸지 말고 product-planner에게 문의한다.

## 이 문서 읽는 법 (4차 사이클 기준)

1차(상품 목록)·2차(상세 + 장바구니)·3차(비우기 + 수량 할인) 사이클의 내용은 **그대로 유효하며 재구현 대상이 아니다.** 이미 구현·검증·커밋이 끝났다.
4차 사이클에서 새로 추가된 것은 **15장 이후**와 데이터 모델의 `Order`다.

> ## ⛔ 4차 사이클 최상단 제약 — 반드시 먼저 읽을 것
>
> **이번에 만드는 결제는 "모의 결제(mock checkout) — 외부 PG 미연동"이다.**
>
> 토스페이먼츠·아임포트(포트원)·KG이니시스·나이스페이·PayPal·Stripe 등 **어떤 결제대행사(PG)와도 연동하지 않는다.** 사용자가 명시적으로 확정한 범위 제약이다.
>
> 구체적으로 아래를 **하나도 만들지 않는다.**
>
> | 만들지 않는 것 | 왜 |
> |---|---|
> | PG SDK·스크립트 로드 (`<script src="https://js.tosspayments.com/...">` 등) | 외부 의존이 생기는 순간 로컬 QA가 네트워크·가맹점키에 묶인다 |
> | 카드번호 / 유효기간 / CVC / 생년월일 / 카드사 선택 입력란 | 결제 수단은 16.7의 라디오 2개가 전부다. **실제 결제 정보를 받는 입력란을 만들지 않는다** |
> | PG 결제창 팝업·리다이렉트·`returnUrl`·`successUrl`/`failUrl` 콜백 페이지 | 이번 흐름에 화면 이탈은 없다. 결제는 `fetch` 한 번으로 끝난다 |
> | 웹훅(webhook) 수신 엔드포인트, 결제 승인 2단계(결제창 → 승인 API) | 서버 안에서 즉시 판정한다 (18.3) |
> | 가맹점 ID / 시크릿 키 / API 키 등 PG 자격증명, `.env` 결제 설정 | 저장할 비밀값 자체가 없다 |
> | 실제 카드 승인·매입·취소·환불·영수증 발급 | 전부 Out of scope |
>
> **대신 이렇게 동작한다:** 프론트가 `POST /api/checkout`을 호출하면 **백엔드가 요청을 받아 그 자리에서 성공/실패를 시뮬레이션해 응답한다.** 판정 근거는 요청의 `paymentMethod` 값 하나이며 결정론적이다 (D17 / 18.3).
>
> backend-agent·frontend-agent 모두, 이 표의 항목 중 하나라도 구현하고 싶어지면 **구현하지 말고 product-planner에게 문의한다.**

## 배경

### 1차 사이클 배경 (2026-08-05)

쇼핑몰 웹사이트의 첫 조각으로, **방문자가 들어오자마자 판매 중인 상품들을 한눈에 볼 수 있는 랜딩(홈) 화면 하나**만 만든다. 전체 MVP(상세/장바구니/결제)를 한 번에 만들면 백엔드·프론트가 서로 다른 걸 상상할 여지가 커지므로, 첫 사이클은 "상품 목록이 화면에 뜬다"는 단 하나의 관찰 가능한 결과로 범위를 좁힌다. 로그인 없이 누구나 접속하면 바로 보이는 단일 스토어프론트이며, 상품 데이터는 미리 심어둔 시드(seed) 데이터를 사용한다.

### 1차 사이클의 확정 결정 (사용자 확인 완료, 재논의 불필요)

| # | 결정 사항 | 결정 | 사유 |
|---|---|---|---|
| D1 | 로그인/회원 | **없음.** 인증 없는 단일 스토어프론트 | 화면·API가 절반으로 줄고, 세션/권한 경계면 버그가 아예 발생하지 않음 |
| D2 | 상품 데이터 출처 | **서버 내장 시드(mock) 데이터.** 관리자 등록 화면 없음 | 목록 화면 검증에 DB나 어드민이 필요 없음. DB 도입은 다음 사이클로 미룸 |

### 2차 사이클 배경 (2026-08-08 추가)

1차에서 만든 목록 화면 위에 **"상품을 눌러보고 → 담고 → 담은 걸 확인한다"**는 하나의 흐름을 얹는다.
즉 이번 사이클의 관찰 가능한 결과는 **"상품 카드를 클릭해 상세로 들어가 장바구니에 담고, 장바구니 화면에서 수량을 바꾸고 지울 수 있으며, 새로고침해도 담은 게 그대로 있다"** 이다.
결제는 이 흐름의 **다음 사이클**로 명시적으로 미룬다 — 결제를 같이 넣으면 이번 사이클의 검증 대상이 두 배가 되고, 장바구니가 제대로 도는지 확인하기 전에 결제 버그를 디버깅하게 된다.

### 2차 사이클의 확정 결정 (사용자 확인 완료, 재논의 불필요)

| # | 결정 사항 | 결정 | 사유 |
|---|---|---|---|
| D4 | 장바구니 저장 위치 | **서버 측 저장.** 프론트의 `localStorage`/`sessionStorage` 사용 **금지** | "새로고침해도 유지"가 요구사항인데 저장 주체가 둘이면(브라우저+서버) 반드시 동기화 버그가 난다. 저장은 서버 한 곳뿐이고 프론트는 항상 서버 응답을 그대로 그린다 |
| D5 | 세션 식별 방식 | **랜덤 `cartId` 쿠키.** 서버가 최초 장바구니 요청 시 UUID를 발급해 `Set-Cookie`로 내려주고, 서버 메모리의 `Map<cartId, CartItem[]>`에 장바구니를 보관 | 아래 "D5 선택 사유" 참고 |
| D6 | 저장 매체 | **서버 프로세스 메모리** (DB 없음). **서버를 재시작하면 장바구니가 비워져도 된다** | "새로고침 후 유지"가 요구사항이지 "서버 재시작 후 유지"는 요구사항이 **아니다.** DB를 넣으면 이번 사이클 검증과 무관한 스키마·마이그레이션이 따라온다 (D2의 시드 데이터 결정과 같은 이유) |
| D7 | 장바구니 담기 진입점 | **상품 상세 화면에서만.** 목록 카드에는 "장바구니 담기" 버튼을 두지 않는다 | 카드 안에 링크(이동)와 버튼(담기) 두 개의 클릭 대상이 겹치면 "카드를 눌렀는데 담겼다/안 담겼다"는 경계면 버그가 난다. 담는 경로를 하나로 고정하면 QA 경로도 하나다 |
| D8 | 장바구니 줄(line) 식별자 | **`productId` 하나로 식별.** 별도 `cartItemId` 없음. 같은 상품을 또 담으면 **새 줄이 생기지 않고 기존 줄의 수량이 증가** | 옵션(사이즈/색상)이 없어서 같은 상품의 줄이 두 개일 이유가 없다. 줄 식별자가 productId면 URL이 `/api/cart/items/p1`로 끝나고, 프론트가 별도 id를 보관·추적할 필요가 없다 |
| D9 | 화면 라우팅 방식 | **정적 다중 페이지.** `/` (목록), `/product.html?id={id}` (상세), `/cart.html` (장바구니) | 1차의 "빌드 도구 없는 정적 HTML + 바닐라 JS" 스택을 그대로 유지. 이 형태면 Express의 `express.static`만으로 서빙되어 **서버 라우팅 설정을 한 줄도 추가하지 않아도 된다.** 새로고침·뒤로가기가 브라우저 기본 동작으로 동작하므로 SPA 라우터를 직접 구현할 때 생기는 버그가 원천적으로 없다 |

#### D5 선택 사유 (backend-agent가 그대로 구현할 것)

이 프로젝트에는 로그인/회원이 없으므로(D1) "누구의 장바구니인가"를 정할 장치가 필요하다. 두 가지 후보를 검토했다.

| 후보 | 장점 | 채택 여부 |
|---|---|---|
| **전역 단일 장바구니** (모든 방문자가 같은 장바구니 공유) | 구현이 제일 짧음 (변수 하나) | ❌ **탈락.** 브라우저 두 개(또는 시크릿 창)를 열면 남의 장바구니가 보인다. 특히 qa-agent가 테스트를 두 번 돌리면 **이전 회차의 담긴 상품이 남아 있어** 검증 결과가 회차마다 달라진다 — 재현 불가능한 QA는 QA가 아니다 |
| **랜덤 `cartId` 쿠키 + 서버 메모리 Map** | 브라우저별로 장바구니가 분리되고, 매 QA 회차가 새 쿠키로 시작하면 깨끗한 상태에서 검증 가능 | ✅ **채택.** 추가 비용은 쿠키 파싱 + `crypto.randomUUID()` 정도이며, 로그인 없이도 "내 장바구니"가 성립한다 |

즉 **가장 짧은 것이 아니라, 가장 짧으면서 검증이 재현 가능한 쪽**을 골랐다. 쿠키 상세 규격은 9.11과 데이터 모델의 "세션 쿠키" 표에 있다.

### 3차 사이클 배경 (2026-08-09 추가)

### 4차 사이클 배경 (2026-08-10 추가)

1~3차로 **"보고 → 담고 → 확인하고 → 수량을 조절한다"**까지가 완성됐다. 원래 MVP 범위에 있던 조각 중 마지막으로 남은 것이 **모의 결제**다. 이번 사이클로 스토어프론트의 한 바퀴가 닫힌다.

이번 사이클의 관찰 가능한 결과는 **"장바구니에서 결제 화면으로 넘어가 주문자 정보를 넣고 결제하면, 성공 시 주문번호가 찍힌 주문 확인 화면으로 이동하고 장바구니가 비워지며, 실패 시 결제 화면에 남아 장바구니가 그대로 유지된 채 재시도할 수 있다"** 이다.

#### D17 선택 사유 (성공/실패를 어떻게 시뮬레이션할 것인가)

사용자에게 되물을 수 없는 항목이라 product-planner가 판단했다. 세 후보를 검토했다.

| 후보 | 검토 | 채택 여부 |
|---|---|---|
| **① 항상 성공** | 구현이 제일 짧다 | ❌ **탈락.** 실패 경로에 코드가 한 줄도 안 생기고, 이번 사이클의 절반(실패 시 장바구니 유지·재시도·에러 표시)이 **검증 불가능**해진다. 결제에서 정작 위험한 쪽은 실패 경로다 |
| **② 임의 실패율 (예: 20% 확률로 실패)** | "진짜 같다" | ❌ **탈락.** 2차 D5에서 이미 못 박은 원칙 — **재현 불가능한 QA는 QA가 아니다.** 같은 테스트가 회차마다 다른 결과를 내면 실패했을 때 "버그인지 확률인지" 판정할 수 없고, qa-agent는 실패 케이스를 확실히 만들려고 재시도 루프를 짜게 된다. 자동화 테스트(`tests/e2e/*.spec.js`)에 랜덤을 넣으면 그 파일은 그날부터 flaky가 된다 |
| **③ 요청 값으로 결정되는 결정론적 판정** (`paymentMethod`가 `MOCK_FAILURE`면 거절) | 100% 재현 가능하고, 실제 PG 테스트 환경에도 "실패를 유발하는 테스트 카드번호"라는 같은 패턴이 있다 | ✅ **채택** |

③ 안에서도 "무엇으로 판정할지"를 한 번 더 골랐다. 주문자 이름에 매직값(예: `"실패테스트"`)을 넣는 방식은 **정상 입력값과 제어값이 같은 칸에 섞여** 나중에 이름이 그 값인 사용자가 결제를 못 하게 되고, 화면만 봐서는 왜 실패했는지 알 수 없다. 반면 **결제 수단은 원래 "결제 결과에 영향을 주는 선택지"** 라서 제어값을 두기에 의미상 가장 자연스러운 자리이고, 라디오 두 개가 화면에 보이므로 **qa-agent도 사람도 실패를 한 번의 클릭으로 재현**할 수 있다.

> ⚠️ **결정론이라고 해서 프론트가 결과를 미리 알아도 된다는 뜻이 아니다.** `MOCK_FAILURE`가 선택돼 있어도 프론트는 **반드시 서버에 요청을 보내고**, 서버의 402 응답을 받아 실패를 표시해야 한다 (16.9). 프론트가 지레 실패 처리하면 이번 사이클이 검증하려는 서버-프론트 경계면이 통째로 테스트되지 않은 채 남는다.

#### D18 선택 사유 (결제 요청에 무엇을 받을 것인가)

회원이 없는 MVP(D1)라 "저장된 주소를 불러온다"는 선택지가 없다. 두 극단 사이에서 정했다.

- **아무것도 안 받는다(버튼만)** → 결제 화면이 버튼 하나가 되어 **400(입력 검증) 케이스가 통째로 사라진다.** 결제 화면은 원래 사용자 입력을 받는 화면인데 그 성질을 검증하지 못한다.
- **실제 주문서처럼 다 받는다(수령인·우편번호·주소·상세주소·요청사항·이메일)** → 우편번호 검색(외부 API), 주소 형식 검증, 배송비 계산이 줄줄이 따라온다. **배송 관련은 3차까지 Out of scope에 명시돼 있었고**, 이번 요청은 배송이 아니라 결제다.

그래서 **"주문이 성립하려면 최소한 있어야 하는 것"** 두 개만 받는다 — **누가 주문했고(이름), 연락이 되는가(연락처).** 배송지가 없어도 주문·결제·주문 확인 흐름은 완결되며, 이 두 필드만으로도 400 검증 케이스가 **필수 누락 / 길이 초과 / 형식 불일치** 세 종류나 생겨 검증 가치가 충분하다. **배송지는 배송 기능을 하는 사이클에 함께 넣는다** (지금 넣으면 아무 데도 쓰이지 않는 입력란이 된다).

## 화면 목록

| 화면 | 경로 | 사이클 |
|---|---|---|
| **상품 목록(홈)** | `/` | 1차 (완료) |
| **상품 상세** | `/product.html?id={productId}` | 2차 (완료) |
| **장바구니** | `/cart.html` | 2차 (완료) · 3차에 내부 변경 |
| **결제(모의)** | `/checkout.html` | **4차 (신규)** |
| **주문 확인** | `/order.html?orderId={orderId}` | **4차 (신규)** |

**4차 사이클의 화면은 위 5개가 전부다.** 신규는 `/checkout.html`과 `/order.html` 2개이며, 기존 3개 화면 중 변경되는 곳은 **장바구니 화면에 "결제하기" 링크 하나가 추가되는 것뿐**이다 (15.1). 목록·상세 화면은 **한 줄도 바뀌지 않는다.**

> 1차 문구였던 "이번 사이클의 화면은 1개가 전부다"와 2차 문구 "위 3개가 전부다 / 결제 화면은 만들지 않는다"는 위 표로 대체된다.
>
> **화면 전이 흐름 (4차 기준)**
>
> ```
>   /              /product.html?id=..        /cart.html            /checkout.html         /order.html?orderId=..
>  목록  ──카드클릭──▶  상세  ──담기(머무름)──▶  장바구니  ──결제하기──▶   결제(모의)   ──승인 성공──▶   주문 확인
>                                                  ▲                      │
>                                                  └──── 장바구니로 ◀──────┤
>                                                                         │
>                                                   승인 거절(402) ────────┘  화면에 머무르며 재시도
>                                                   (장바구니는 그대로 유지)
> ```
>
> - 결제 화면으로 들어가는 문은 **장바구니 화면 하나뿐**이다. 상세 화면의 "바로 구매"는 만들지 않는다 (6.12 유지 / 15.3).
> - 주문 확인 화면으로 가는 이동은 **승인 성공 시에만** 일어난다. 실패하면 화면을 옮기지 않는다 (16.11 / 16.12).

## 기능 요구사항

각 항목은 qa-agent의 검증 기준이 되는 번호다. 문제 보고 시 이 번호로 지칭한다.

### 1. 상품 목록(홈) 화면

- **1.1** 사용자가 `/`에 접속하면, 서버에서 상품 목록을 조회해 상품 카드들이 화면에 나열되어야 한다.
- **1.2** 각 상품 카드는 **상품 이미지, 상품명, 가격** 3가지를 반드시 표시해야 한다. (설명 `description`은 표시 여부를 frontend-agent 재량에 맡긴다)
- **1.3** 가격은 원화 정수를 천 단위 구분 기호와 함께 표시해야 한다. 예: `price: 12000` → 화면에는 `12,000원`. 소수점은 표시하지 않는다.
- **1.4** 상품 이미지(`imageUrl`)를 불러오지 못하면 카드 레이아웃이 깨지지 않고 대체(placeholder) 영역이 자리를 유지해야 한다.
- **1.5** 상품 카드는 그리드로 배치되어야 하며, 브라우저 폭이 좁아져도(모바일 폭 375px 기준) 카드가 가로로 잘리거나 겹치지 않아야 한다.
- **1.6** ~~**상품 카드를 클릭해도 아무 화면으로도 이동하지 않아야 한다.** 상세 화면이 이번 범위에 없으므로, 클릭 가능한 링크(`<a href>`)나 "장바구니 담기" 버튼을 만들지 않는다.~~ (frontend-agent가 습관적으로 상세 링크를 넣는 것을 막기 위한 명시적 요구사항)

  > 🔁 **[2차 사이클 개정 — 2026-08-08] 1.6은 폐기되고 5.1로 대체된다.** 상세 화면이 생겼으므로 **카드는 상세로 이동하는 링크가 되어야 한다.** 단 "장바구니 담기 버튼을 카드에 넣지 않는다"는 제약은 **그대로 유지**된다 (D7 / 5.2). 즉 카드에서 허용되는 클릭 동작은 **상세 이동 하나뿐**이다.

### 2. 상태 처리 (로딩 / 빈 목록 / 에러)

- **2.1** 상품 목록 응답을 기다리는 동안 로딩 상태(스켈레톤 또는 "불러오는 중" 표시)가 화면에 보여야 한다.
- **2.2** 상품이 0개인 경우(`items`가 빈 배열), 에러가 아니라 "판매 중인 상품이 없습니다" 같은 빈 상태 메시지가 표시되어야 한다. 이때 화면에 상품 카드는 0개여야 한다.
- **2.3** 상품 목록 API 호출이 실패하면(네트워크 오류 또는 HTTP 5xx), "상품을 불러오지 못했습니다" 같은 에러 메시지가 표시되어야 하며, 빈 화면이나 깨진 화면이 되면 안 된다.
- **2.4** 로딩/빈 상태/에러 상태 세 가지는 서로 배타적이어야 한다 — 동시에 두 개 이상이 화면에 보이면 안 된다.

### 3. 상품 목록 API

- **3.1** `GET /api/products` 요청 시 200과 함께 `{ "items": [...] }` 형태로 상품 배열을 반환해야 한다. **배열을 그대로(top-level array) 반환하지 않는다.**
- **3.2** 상품이 0개일 때도 200과 `{ "items": [] }`를 반환해야 한다. 404나 에러가 아니다.
- **3.3** 배열의 각 요소는 아래 "데이터 모델" 표의 5개 필드(`id`, `name`, `price`, `imageUrl`, `description`)를 **모두** 포함해야 하며, 필드를 생략하거나 `null`로 두지 않는다.
- **3.4** 서버 내부 오류 시 5xx 상태 코드와 함께 `{ "error": { "message": "..." } }`를 반환해야 한다. 오류를 200으로 반환하면서 body로만 표시하면 안 된다.
- **3.5** 시드 데이터는 **최소 6개 이상**의 상품을 포함해야 한다 (그리드 레이아웃 및 1.5 검증을 위한 최소 수량).
- **3.6** ~~이번 범위에서 `GET /api/products` 외의 API는 구현하지 않는다. (상세/장바구니/결제 엔드포인트 없음)~~

  > 🔁 **[2차 사이클 개정 — 2026-08-08] 3.6은 9.12로 대체된다.** 이번 범위의 API는 `GET /api/products` + 9장의 신규 5개, **총 6개**다. **결제(`/api/checkout`) 엔드포인트는 여전히 만들지 않는다.**

### 4. 테스트 선택자

- **4.1** 상품 목록 컨테이너에 `data-testid="product-list"`가 있어야 한다.
- **4.2** 각 상품 카드에 `data-testid="product-card"`와 `data-product-id="{id}"`가 있어야 한다.
- **4.3** 카드 내부 요소에 각각 `data-testid="product-name"`, `data-testid="product-price"`, `data-testid="product-image"`가 있어야 한다.
- **4.4** 로딩/빈 상태/에러 상태 요소에 각각 `data-testid="loading-state"`, `data-testid="empty-state"`, `data-testid="error-state"`가 있어야 한다.

## 기능 요구사항 — 2차 사이클 추가분 (2026-08-08)

아래 5~10장은 이번 사이클에 새로 구현할 범위다. 1~4장은 이미 구현·검증이 끝났으므로 **회귀(regression)만 확인하면 되고 다시 만들지 않는다.**

### 5. 목록 화면의 변경 (1.6 개정분) 및 공통 헤더

- **5.1** 상품 목록에서 상품 카드를 클릭하면 **해당 상품의 상세 화면(`/product.html?id={상품의 id}`)으로 이동해야 한다.** 카드 전체가 클릭 영역이어야 하며, 이동 수단은 실제 `<a href>` 링크여야 한다 (JS `onclick`만으로 `location`을 바꾸지 않는다 — 새 탭 열기·뒤로가기가 브라우저 기본 동작으로 되어야 하기 때문).
- **5.2** 상품 카드 안에 **"장바구니 담기" 버튼을 두지 않는다** (D7). 목록 화면에서 카드에 대해 가능한 클릭 동작은 상세 이동 **하나뿐**이어야 한다.
- **5.3** 카드를 링크로 감싸더라도 기존 테스트 선택자 위치는 **변하지 않아야 한다** — `data-testid="product-card"`와 `data-product-id="{id}"`는 4.2가 정한 그대로 카드 요소에 있어야 하고, 4.3의 `product-name` / `product-price` / `product-image`도 카드 내부에 그대로 있어야 한다.
- **5.4** 세 화면(목록/상세/장바구니) 모두 상단에 **장바구니로 가는 링크**가 있어야 하며, 그 안에 현재 담긴 **총 수량(`totalQuantity`)** 이 표시되어야 한다.
- **5.5** 총 수량이 0이면 수량 배지는 화면에 보이지 않아야 한다(요소는 DOM에 남기고 `hidden` 처리). 0보다 크면 숫자가 그대로 보여야 한다. 예: 2개짜리 1줄 + 3개짜리 1줄 → `5`.
- **5.6** 장바구니 담기·수량 변경·삭제 후에는 **같은 화면 안에서 이 수량 배지가 즉시 갱신되어야 한다** (새로고침 없이). 배지 값은 서버 응답의 `cart.totalQuantity`를 그대로 쓰며 프론트에서 따로 계산하지 않는다.
- **5.7** 목록 화면 진입 시에도 배지를 채우기 위해 `GET /api/cart`를 호출한다. 이 호출이 실패하더라도 **상품 목록 렌더링은 정상적으로 되어야 한다** (배지만 숨김). 장바구니 조회 실패가 목록 화면 전체를 에러 상태로 만들면 안 된다.

### 6. 상품 상세 화면

- **6.1** `/product.html?id={productId}`에 접속하면 `GET /api/products/{productId}`를 호출해 **상품 이미지, 상품명, 가격, 설명 4가지를 모두** 화면에 표시해야 한다. (목록 카드와 달리 `description`은 상세에서 **필수 표시**다)
- **6.2** 가격 표기는 1.3과 동일하다 — `19000` → `19,000원`. 소수점 없음.
- **6.3** 상세 화면에는 **수량 선택 UI**가 있어야 하며, 초기값은 `1`, 허용 범위는 **1 이상 99 이하의 정수**다. 값이 1일 때 감소(−) 조작은 동작하지 않아야 하고(0이나 음수가 될 수 없다), 99일 때 증가(+) 조작도 동작하지 않아야 한다.
- **6.4** **"장바구니 담기" 버튼**을 클릭하면 `POST /api/cart/items`를 `{ "productId": "{id}", "quantity": {선택 수량} }`으로 호출해야 한다.
- **6.5** 담기에 성공하면 (a) "장바구니에 담았습니다" 같은 성공 피드백이 화면에 표시되고, (b) 상단 장바구니 수량 배지가 갱신되어야 한다. **자동으로 장바구니 화면으로 이동하면 안 된다** — 사용자는 상세 화면에 그대로 머문다. (이동은 사용자가 장바구니 링크를 눌렀을 때만)
- **6.6** 같은 상품을 **두 번 담으면** 장바구니에 줄이 두 개 생기는 것이 아니라 **기존 줄의 수량이 합산**되어야 한다 (D8). 예: 2개 담고 다시 3개 담으면 → 그 상품 1줄, 수량 `5`.
- **6.7** 담기 요청이 실패하면(4xx/5xx/네트워크 오류) 에러 메시지가 표시되어야 하고, **수량 배지는 갱신되지 않아야 한다** (담기지도 않았는데 담긴 것처럼 보이면 안 된다).
- **6.8** 존재하지 않는 `id`로 접속하면(API가 404 응답) **"상품을 찾을 수 없습니다" 같은 not-found 상태**가 표시되어야 하며, 목록으로 돌아가는 링크가 함께 있어야 한다. 빈 화면이나 깨진 화면이 되면 안 된다.
- **6.9** `?id=`가 아예 없거나 빈 문자열이면 API를 호출하지 않고 곧바로 6.8과 같은 not-found 상태를 표시해야 한다.
- **6.10** 상세 화면의 상태(로딩 / 정상 / not-found / 에러)는 **서로 배타적이어야 한다** — 동시에 두 개 이상이 보이면 안 된다 (2.4와 같은 규칙).
- **6.11** 상세 화면에는 **목록으로 돌아가는 링크**가 있어야 한다.
- **6.12** 상세 화면에 결제/구매 관련 버튼("바로 구매", "결제하기" 등)을 만들지 않는다 (Out of scope).

### 7. 장바구니 화면

- **7.1** `/cart.html`에 접속하면 `GET /api/cart`를 호출해 담긴 항목들을 줄 단위로 나열해야 한다. 각 줄은 **상품 이미지, 상품명, 단가(`price`), 수량(`quantity`), 줄 합계(`lineTotal`)** 5가지를 표시해야 한다.
- **7.2** 어떤 줄의 수량을 변경하면 `PATCH /api/cart/items/{productId}`를 `{ "quantity": {변경 후 수량} }`으로 호출해야 한다. **보내는 값은 증감분(delta)이 아니라 변경 후의 절대 수량이다.**
- **7.3** 수량 변경이 성공하면 그 줄의 수량·줄 합계, 그리고 **총 수량·총 금액이 함께 갱신되어야 한다.** 갱신 값은 응답으로 받은 `cart` 스냅샷을 그대로 다시 그린 결과여야 한다.
- **7.4** 수량은 **1 이상 99 이하**로만 변경할 수 있다. 수량이 1인 줄에서 감소(−) 조작은 동작하지 않아야 한다 — **수량을 0으로 만들어 항목을 지우는 경로는 없다.** 항목 제거는 7.5의 삭제 조작으로만 한다.
- **7.5** 각 줄에 **삭제 버튼**이 있어야 하며, 클릭하면 `DELETE /api/cart/items/{productId}`를 호출하고 성공 시 그 줄이 화면에서 사라지고 총 수량·총 금액이 갱신되어야 한다.
- **7.6** 화면에 **총 수량(`totalQuantity`)과 총 금액(`totalPrice`)** 이 표시되어야 한다. 총 금액은 1.3과 동일한 포맷(`97,000원`)으로 표시하며, **값은 서버 응답의 `totalPrice`를 그대로 쓰고 프론트에서 다시 합산하지 않는다** (합산 로직이 두 군데 있으면 두 값이 어긋나는 순간 어느 쪽이 맞는지 판정 불가능해진다).

  > 🔁 **[3차 사이클 보강 — 2026-08-09]** 7.6은 **그대로 유효하며 더 중요해진다.** 3차부터 `totalPrice`는 **할인이 반영된 금액**이다(12.6). 프론트가 `price × quantity`를 더해서 총액을 만들면 할인 줄에서 반드시 값이 어긋난다. **서버 값을 그대로 출력하는 것 외의 경로는 없다.**
- **7.7** 장바구니가 비어 있으면(`cart.items`가 빈 배열) 에러가 아니라 **"장바구니가 비어 있습니다" 같은 빈 상태 메시지**와 상품 목록으로 가는 링크가 표시되어야 하고, 이때 **합계 요약 영역은 화면에 보이지 않아야 한다.**
- **7.8** 마지막 항목을 삭제하면 별도 새로고침 없이 곧바로 7.7의 빈 상태로 전환되어야 한다.
- **7.9** 장바구니 조회/변경 요청이 실패하면 에러 메시지가 표시되어야 하며, 화면이 비거나 깨지면 안 된다. 로딩 / 목록 / 빈 상태 / 에러 네 상태는 **서로 배타적**이어야 한다.
- **7.10** ~~장바구니 화면에 **결제/주문 버튼을 만들지 않는다** (Out of scope). 다음 사이클에서 추가된다.~~

  > 🔁 **[4차 사이클 개정 — 2026-08-10] 7.10은 폐기되고 15.1로 대체된다.** 여기서 말한 "다음 사이클"이 곧 4차다. 장바구니 화면에 **"결제하기" 링크(`checkout-link`)가 생긴다.** 단 **결제 진입점은 여전히 장바구니 화면 하나뿐**이며, 상세 화면의 결제 버튼 금지(6.12)는 **그대로 유지된다** (15.3).

### 8. 장바구니 세션 및 영속성

- **8.1** 장바구니 내용은 **서버에 저장되어야 한다.** 프론트엔드는 장바구니 상태를 `localStorage`·`sessionStorage`·전역 변수에 **보관하지 않는다** — 화면은 항상 서버 응답을 그대로 그린다 (D4).
- **8.2** 서버는 장바구니 관련 요청에서 `cartId` 쿠키가 없으면 **새 임의 식별자를 발급해 `Set-Cookie`로 내려주고**, 그 이후 요청부터는 브라우저가 자동으로 보내는 같은 쿠키로 장바구니를 식별해야 한다 (D5).
- **8.3** **상품을 담은 뒤 페이지를 새로고침(F5)해도, 그리고 목록 → 상세 → 장바구니로 화면을 옮겨다녀도 담긴 내용과 수량이 그대로 유지되어야 한다.** (이번 사이클의 핵심 검증 항목)
- **8.4** 브라우저를 닫았다 다시 열어도(쿠키 유효기간 내) 장바구니가 유지되어야 한다. 쿠키 유효기간은 **7일**로 한다.
- **8.5** **서로 다른 브라우저(또는 시크릿 창)는 서로 다른 장바구니를 가져야 한다.** 한쪽에서 담은 상품이 다른 쪽 장바구니에 보이면 안 된다.
- **8.6** 프론트엔드는 쿠키를 직접 읽거나 쓰지 않는다. `document.cookie`를 다루는 코드를 작성하지 않으며, 같은 오리진 `fetch`의 기본 쿠키 동작에 의존한다 (1차에서 정한 단일 서버·단일 포트 구성이라 별도 CORS/`credentials` 설정이 필요 없다).
- **8.7** **서버 프로세스를 재시작하면 장바구니가 비워져도 된다.** 이는 허용된 동작이며 버그가 아니다 (D6). qa-agent는 "서버 재시작 후에도 유지"를 검증 항목으로 삼지 않는다.

### 9. 신규 API

기존 `GET /api/products`(3.1~3.5)는 **응답 shape을 포함해 하나도 바뀌지 않는다.** 아래는 추가되는 엔드포인트다.

| # | Method | Path | 역할 |
|---|---|---|---|
| 9.1 | GET | `/api/products/:id` | 상품 1건 조회 |
| 9.3 | GET | `/api/cart` | 장바구니 조회 |
| 9.4 | POST | `/api/cart/items` | 장바구니에 담기 |
| 9.5 | PATCH | `/api/cart/items/:productId` | 줄 수량 변경 |
| 9.6 | DELETE | `/api/cart/items/:productId` | 줄 삭제 |

- **9.1** `GET /api/products/:id` 요청 시 해당 상품이 있으면 200과 함께 **`{ "item": { ...5개 필드 } }`** 를 반환해야 한다. **상품 객체를 top-level로 그대로 반환하지 않는다** (목록의 `items` 래핑과 같은 원칙 — 3.1). `item`의 필드 구성은 3.3과 동일한 5개(`id`, `name`, `price`, `imageUrl`, `description`)다.
- **9.2** 존재하지 않는 `id`이면 **404**와 함께 `{ "error": { "message": "..." } }`를 반환해야 한다. 200에 빈 객체를 담아 보내지 않는다.
- **9.3** `GET /api/cart`는 **항상 200**과 함께 아래 "장바구니 응답 shape"을 반환해야 한다. 장바구니가 비어 있어도 404가 아니라 200 + `{ "cart": { "items": [], "totalQuantity": 0, "totalPrice": 0 } }`이다.
- **9.4** `POST /api/cart/items`는 `{ "productId": string, "quantity": integer }`를 받는다. `quantity`가 생략되면 **1**로 간주한다. 성공 시 **200**과 함께 **변경 후 장바구니 전체 스냅샷**을 반환해야 한다.
- **9.5** `PATCH /api/cart/items/:productId`는 `{ "quantity": integer }`를 받으며, 이 값은 **변경 후의 절대 수량**이다(증감분이 아니다). 성공 시 200 + 변경 후 장바구니 전체 스냅샷.
- **9.6** `DELETE /api/cart/items/:productId`는 해당 줄을 제거하고 200 + 변경 후 장바구니 전체 스냅샷을 반환한다. 204 No Content를 반환하지 않는다 — 프론트가 갱신된 총액을 받으려면 body가 필요하다.
- **9.7** **9.3~9.6 네 엔드포인트는 모두 완전히 동일한 응답 shape(`{ "cart": {...} }`)을 반환해야 한다.** 프론트는 어떤 조작을 하든 같은 렌더 함수 하나로 화면을 다시 그릴 수 있어야 한다.
- **9.8** ~~`lineTotal`(= `price × quantity`)~~, `totalQuantity`(= 모든 줄의 `quantity` 합), `totalPrice`(= 모든 줄의 `lineTotal` 합)는 **서버가 계산해서 응답에 담아야 한다.** 프론트가 계산하도록 남겨두지 않는다 (7.6).

  > 🔁 **[3차 사이클 개정 — 2026-08-09] `lineTotal = price × quantity`는 폐기되고 12.5로 대체된다.** `lineTotal`은 이제 **할인 후** 줄 금액이다. 할인 전 금액은 새 필드 `lineSubtotal`이 담는다. **"서버가 모든 금액을 계산한다"는 원칙 자체는 그대로이고, 계산 대상 필드가 6개로 늘어난다** (13.7).
- **9.9 (검증 규칙)** 아래 경우 **400**과 `{ "error": { "message": "..." } }`를 반환해야 한다.
  - `productId`가 없거나 문자열이 아닐 때
  - `quantity`가 정수가 아닐 때(소수·문자열 `"2"`·`NaN` 포함)
  - `quantity < 1` 또는 `quantity > 99`일 때 — **특히 `quantity: 0`은 "삭제"로 처리하지 않고 400이다** (삭제는 9.6으로만 한다. 같은 결과에 이르는 경로가 둘이면 프론트가 어느 쪽을 쓸지 갈린다)
- **9.10 (없는 대상)** 아래 경우 **404**와 `{ "error": { "message": "..." } }`를 반환해야 한다.
  - `POST /api/cart/items`의 `productId`가 시드 상품에 없는 값일 때
  - `PATCH`/`DELETE`의 `:productId`가 **현재 장바구니에 담겨 있지 않을** 때
- **9.11 (쿠키)** 위 장바구니 엔드포인트들은 `cartId` 쿠키가 없으면 새로 발급해 응답에 `Set-Cookie`로 실어야 한다. 쿠키 속성은 **`Path=/`, `HttpOnly`, `SameSite=Lax`, `Max-Age=604800`(7일)** 로 하고, 로컬 http 환경이므로 **`Secure`는 붙이지 않는다**(붙이면 `http://localhost`에서 쿠키가 저장되지 않아 장바구니가 매 요청 초기화된다).
- **9.12 (범위 제한)** ~~이번 사이클의 API는 `GET /api/products` + 위 5개 = **총 6개가 전부다.** 특히 `POST /api/checkout`, `DELETE /api/cart`(전체 비우기), 주문 관련 엔드포인트는 **구현하지 않는다.**~~

  > 🔁 **[3차 사이클 개정 — 2026-08-09] 9.12는 13.8로 대체된다.** `DELETE /api/cart`(전체 비우기)가 범위로 편입되어 **총 7개**가 된다. **`POST /api/checkout`과 주문 관련 엔드포인트는 여전히 구현하지 않는다.**
- **9.13** 모든 에러 응답은 1차와 동일하게 `{ "error": { "message": "..." } }` 형태이며, 에러를 200으로 반환하면서 body로만 표시하면 안 된다 (3.4와 같은 규칙).

**새로 만드는 화면은 없다.** 변경 지점은 장바구니 화면(`/cart.html`)과 장바구니 API뿐이다.

### 11. 장바구니 전체 비우기

- **11.1** 장바구니 화면에 **"장바구니 비우기" 버튼**이 있어야 하며, 클릭하면 `DELETE /api/cart`를 한 번 호출해야 한다. 줄 개수만큼 `DELETE /api/cart/items/:productId`를 반복 호출하는 방식으로 구현하면 **안 된다** (요청이 N개로 늘어나고, 중간에 하나가 실패하면 절반만 비워진 상태가 된다).
- **11.2** 비우기에 성공하면 모든 줄이 화면에서 사라지고, **새로고침 없이 곧바로 7.7의 빈 상태**("장바구니가 비어 있습니다" + 상품 목록 링크)로 전환되어야 한다. 이때 합계 요약 영역(`cart-summary`)은 7.7대로 화면에서 보이지 않아야 한다.
- **11.3** 비우기에 성공하면 상단 장바구니 수량 배지가 **0이 되어 숨겨져야 한다** (5.5 / 5.6). 배지 값은 응답의 `cart.totalQuantity`(= `0`)를 그대로 쓴다.
- **11.4** **확인 다이얼로그를 만들지 않는다** (D10). `window.confirm`, `window.alert`, 그리고 "정말 비우시겠습니까?" 류의 커스텀 확인 모달 중 **어느 것도 만들지 않는다.** 클릭 한 번이 곧 실행이다.
- **11.5** 장바구니가 비어 있을 때(항목 0개) 비우기 버튼은 **화면에 보이지 않아야 한다.** 요소는 DOM에 남기고 `hidden` 처리한다 (10.2의 `cart-count`와 같은 방식). 항목이 1개 이상이면 보여야 한다.
- **11.6** 비우기 요청이 실패하면(4xx / 5xx / 네트워크 오류) 에러 메시지가 표시되어야 하며, **화면의 줄과 합계는 비우기 전 상태 그대로 유지되어야 한다.** 요청을 보내자마자 미리 화면을 비우는 낙관적 갱신(optimistic update)을 하면 안 된다 — 서버가 안 비웠는데 화면만 비면 새로고침 시 상품이 되살아나 사용자가 버그로 인식한다.
- **11.7** 비우기는 화면만 지우는 것이 아니라 **서버의 장바구니 상태를 비우는 것**이다. 비운 뒤 새로고침하거나 다른 화면을 거쳐 돌아와도 빈 상태여야 한다 (8.3과 같은 규칙).
- **11.8** 비우기 버튼은 **장바구니 화면에만** 둔다. 목록 화면·상세 화면·공통 헤더에는 만들지 않는다.

### 12. 수량 기반 자동 할인 (10개 이상 10%)

**규칙 한 줄:** 한 줄의 수량이 **10개 이상**이면, 그 줄 **전체**에 **10%** 할인이 자동으로 적용된다.

#### 12.1~12.4 — 적용 규칙과 경계

- **12.1** 장바구니의 어떤 줄이든 `quantity`가 **10 이상**이면 그 줄에 **10% 할인**이 자동 적용되어야 한다. 쿠폰 입력·적용 버튼 같은 사용자 조작은 **없다** (D13).
- **12.2 (경계값 — off-by-one 금지)** 판정식은 **`quantity >= 10`** 이다. `> 10`이 아니다. 구체적으로:

  | quantity | 할인 | 
  |---|---|
  | 9 | **적용 안 됨** |
  | **10** | **적용됨** ← 경계 |
  | 11 | 적용됨 |
  | 99(상한) | 적용됨 |

  qa-agent는 **9와 10 두 값을 반드시 각각 검증한다.** 이 경계가 한 칸 밀리면 화면상으로는 그럴듯해 보이므로 눈으로는 안 잡힌다.
- **12.3 (줄 전체 적용)** 할인은 그 줄의 **전체 수량**에 적용된다. 10번째를 초과하는 수량에만 적용하는 방식이 **아니다** (D11).
  - 예: `price: 19000`, `quantity: 10` → 줄 합계는 190,000원이 아니라 **171,000원**이다.
  - (참고: 초과분만 할인하는 방식이었다면 9 × 19,000 + 1 × 17,100 = 188,100원이 된다. **이 값이 나오면 틀린 구현이다.**)
- **12.4 (줄 단위 독립 판정)** 할인 여부는 **각 줄이 따로** 판정한다. 장바구니 총 수량(`totalQuantity`)이나 다른 줄의 수량은 **아무 영향도 주지 않는다** (D14).
  - 예: A상품 6개 + B상품 5개(총 11개) → **두 줄 모두 할인 없음.**
  - 예: A상품 10개 + B상품 1개(총 11개) → **A줄만 할인, B줄은 정가.**

#### 12.5~12.6 — 계산식 (서버가 계산한다)

- **12.5** 서버는 각 줄에 대해 아래 순서로 계산해 응답에 담아야 한다. **프론트는 이 중 어떤 값도 직접 계산하지 않는다** (7.6 / D12).

  ```
  discountApplied      = (quantity >= 10)                      // 10 포함
  discountPercent      = discountApplied ? 10 : 0
  lineSubtotal         = price * quantity                       // 할인 전 줄 금액
  discountedUnitPrice  = discountApplied
                           ? price - Math.floor(price * 10 / 100)   // 1원 미만 버림
                           : price
  lineTotal            = discountedUnitPrice * quantity          // 할인 후 줄 금액 (최종)
  discountAmount       = lineSubtotal - lineTotal
  ```

  - **단가를 먼저 깎고 수량을 곱한다.** 줄 합계를 먼저 만든 뒤 깎는 순서로 구현하면 안 된다 (D12) — 그러면 화면의 `할인 단가 × 수량`이 화면의 `줄 합계`와 안 맞는 줄이 생긴다.
  - **반올림이 아니라 버림(`Math.floor`)** 이다. 모든 금액은 원 단위 정수이며, 응답에 소수가 실려서는 안 된다.
  - 검산: `price: 19000`, `quantity: 10` → `discountedUnitPrice = 19000 - 1900 = 17100`, `lineTotal = 171000`, `lineSubtotal = 190000`, `discountAmount = 19000`.
- **12.6 (합계)** `totalPrice`는 **할인이 반영된 `lineTotal`들의 합**이어야 한다. 할인 전 금액(`lineSubtotal`)의 합이 아니다. `totalQuantity`는 할인과 **무관하게** 모든 줄의 `quantity` 합 그대로다 (할인이 수량을 바꾸지는 않는다).

#### 12.7~12.8 — 상태가 바뀌는 순간

- **12.7** 수량 변경(`PATCH`)으로 할인 상태가 **켜지고 꺼져야 한다.** 9 → 10으로 올리면 그 줄에 할인이 켜지고, 10 → 9로 내리면 꺼져야 한다. 두 경우 모두 응답으로 받은 `cart` 스냅샷을 다시 그린 결과가 화면에 반영되어야 하며(7.3), 줄 합계와 총 금액이 함께 바뀌어야 한다.
- **12.8** 담기 합산으로 10에 도달하는 경우도 동일하다. 상세 화면에서 6개를 담고 다시 4개를 담아 그 줄이 10개가 되면(6.6의 합산 규칙), 장바구니 화면에서 그 줄은 **할인 적용 상태로 보여야 한다.**

#### 12.9~12.14 — 화면 표시

- **12.9** 할인이 적용된 줄에는 아래 3가지가 **모두** 표시되어야 한다.
  1. **원래 단가에 취소선** — 예: ~~19,000원~~ (`price` 값, `cart-item-price`)
  2. **할인 적용 단가** — 예: `17,100원` (`discountedUnitPrice` 값, `cart-item-discounted-price`)
  3. **할인 안내 문구** — 예: `10개 이상 10% 할인 적용` (`cart-item-discount-notice`)
- **12.10** 할인이 적용되지 **않은** 줄에는 위 3가지가 **하나도 나타나면 안 된다.** 원래 단가가 취소선 없이 하나만 표시된다. (할인가 요소와 안내 문구 요소는 그 줄의 DOM에 **아예 존재하지 않아야 한다** — 14.4)
- **12.11** 화면이 할인 UI를 그릴지 말지 판정하는 기준은 **응답의 `discountApplied` 필드 하나뿐**이다. 프론트가 `quantity >= 10`을 **다시 판정하지 않는다.** 판정 기준이 서버·프론트 두 곳에 있으면 한쪽만 바뀌는 순간 화면과 금액이 어긋난다 (12.2의 경계가 두 벌 존재하게 된다).
- **12.12** 줄 합계(`cart-item-total`)에는 **할인 후 금액(`lineTotal`) 하나만** 표시한다. 줄 합계 자리에 취소선 친 `lineSubtotal`을 함께 표시하지 않는다 — **취소선은 단가 자리 한 곳에만** 둔다.
- **12.13** 모든 금액 표기는 1.3과 동일한 포맷이다. 예: `171,000원`, `17,100원`. 소수점은 표시하지 않는다.
- **12.14** **상품 상세 화면에는 할인 UI를 만들지 않는다** (D15). 상세에서 수량을 10 이상으로 골라도 할인 표시·예상 금액을 보여주지 않는다. 할인 표시는 **장바구니 화면에만** 있다.
- **12.15 (상수 위치)** 기준 수량(`10`)과 할인율(`10%`)은 **서버 코드의 상수 한 곳**(예: `DISCOUNT_MIN_QUANTITY = 10`, `DISCOUNT_PERCENT = 10`)에 둔다. 화면의 안내 문구도 응답의 `discountPercent`를 사용하고 숫자를 HTML에 직접 박아넣지 않는다.

### 13. API — 3차 추가·변경분

기존 6개 엔드포인트의 **경로·메서드·응답 shape은 하나도 바뀌지 않는다.** 아래 1개가 추가되고, 장바구니 응답의 `CartItem`에 필드 5개가 추가된다.

| # | Method | Path | 역할 |
|---|---|---|---|
| 13.1 | DELETE | `/api/cart` | 장바구니 전체 비우기 (**신규**) |

- **13.1** `DELETE /api/cart`는 현재 `cartId`의 장바구니를 통째로 비우고, **200**과 함께 `{ "cart": { "items": [], "totalQuantity": 0, "totalPrice": 0 } }`를 반환해야 한다. **204 No Content를 반환하지 않는다** — 프론트가 비워진 스냅샷을 그대로 다시 그려야 하기 때문이다 (9.6과 같은 이유).
- **13.2 (멱등성)** 이미 비어 있는 장바구니에 `DELETE /api/cart`를 다시 호출해도 **200 + 빈 장바구니**를 반환해야 한다. 404나 400이 아니다. 몇 번을 호출하든 결과가 같아야 한다.
- **13.3 (쿠키)** `cartId` 쿠키가 없는 상태로 호출되어도 9.11대로 쿠키를 발급하고 빈 장바구니를 반환한다. 에러가 아니다.
- **13.4 (라우팅 주의)** `DELETE /api/cart`와 `DELETE /api/cart/items/:productId`는 **서로 다른 엔드포인트**다. 경로가 겹쳐 한쪽이 다른 쪽을 가로채지 않도록 한다. 특히 `/api/cart/items/` 뒤가 비어 있는 요청이 전체 비우기로 동작하면 **안 된다** (400 또는 404).
- **13.5 (응답 shape 확장)** 9.7의 "모든 장바구니 엔드포인트가 동일한 `{ "cart": {...} }` shape을 반환한다"는 규칙이 **5개 엔드포인트**(9.3~9.6 + 13.1)로 확장된다. 프론트의 렌더 함수는 여전히 하나다.
- **13.6 (할인 필드 필수)** 위 5개 엔드포인트가 반환하는 **모든 `CartItem`은 할인 필드 5개(`lineSubtotal`, `discountApplied`, `discountPercent`, `discountedUnitPrice`, `discountAmount`)를 항상 포함해야 한다.** 할인이 적용되지 않은 줄에서도 **생략하거나 `null`로 두지 않는다** — 값은 데이터 모델 표에 정한 "미적용 시 값"을 그대로 채운다. 프론트에 `undefined` 방어 코드를 쓰게 만들지 않기 위함이다.
- **13.7 (서버 계산 필드 — 9.8 개정판)** 서버가 계산해 응답에 담아야 하는 값은 아래 **줄 단위 6개 + 장바구니 단위 2개**다. 이 중 어느 하나도 프론트 계산에 맡기지 않는다.
  - 줄 단위: `lineSubtotal`, `discountApplied`, `discountPercent`, `discountedUnitPrice`, `discountAmount`, `lineTotal`
  - 장바구니 단위: `totalQuantity`, `totalPrice`
- **13.8 (범위 제한 — 9.12 개정판)** ~~이번 사이클의 API는 `GET /api/products` + 2차의 5개 + `DELETE /api/cart` = **총 7개가 전부다.** 특히 아래는 **여전히 구현하지 않는다.**~~
  - ~~`POST /api/checkout` 및 주문 관련 엔드포인트 전부~~
  - 쿠폰/프로모션 코드 관련 엔드포인트 (`POST /api/cart/coupon` 등)
  - 할인 규칙을 조회·변경하는 엔드포인트 (할인율은 서버 상수다 — 12.15)

  > 🔁 **[4차 사이클 개정 — 2026-08-10] 13.8은 18.13으로 대체된다.** `POST /api/checkout`과 `GET /api/orders/:orderId` 2개가 추가되어 **총 9개**가 된다. **쿠폰·할인 규칙 엔드포인트는 여전히 만들지 않으며**, 주문 관련 중에서도 **주문 목록 `GET /api/orders`(복수형)·주문 취소·환불은 만들지 않는다** (단건 조회만 편입).
- **13.9** 검증 실패·없는 대상·에러 응답 규격(9.9 / 9.10 / 9.13)은 그대로다. 할인 때문에 새로 생기는 400/404 케이스는 **없다** — 할인은 사용자가 입력하는 값이 아니라 수량에서 파생되는 값이기 때문이다.

### 14. 테스트 선택자 (3차 추가분)

4.1~4.4와 10.1~10.13은 **그대로 유지된다.** 아래가 추가된다.

- **14.1** 장바구니 비우기 버튼에 `data-testid="cart-clear"`가 있어야 한다. **항목이 0개일 때도 요소는 DOM에 남고 `hidden` 처리만 된다** (11.5, 10.2의 `cart-count`와 같은 규칙).
- **14.2** 할인 적용 단가 요소에 `data-testid="cart-item-discounted-price"`가 있어야 한다. 값은 `discountedUnitPrice`를 1.3 포맷으로 표시한 것(예: `17,100원`)이다.
- **14.3** 할인 안내 문구 요소에 `data-testid="cart-item-discount-notice"`가 있어야 한다. 문구는 `10개 이상 10% 할인 적용` 형태이며, 숫자는 응답의 `discountPercent`를 사용한다 (12.15).
- **14.4 (존재/부재로 판정한다)** 14.2와 14.3의 두 요소는 **할인이 적용된 줄에만 DOM에 존재해야 하고, 적용되지 않은 줄에는 아예 존재하지 않아야 한다.** (`hidden` 처리가 아니라 **부재**다.) 줄은 스냅샷을 받을 때마다 다시 그려지므로 부재가 자연스럽고, qa-agent가 "요소 개수"만으로 할인 줄 수를 셀 수 있다.

  > ⚠️ 14.1(`cart-clear`)은 **DOM에 남기고 hidden**, 14.2·14.3은 **DOM에서 부재**다. 규칙이 서로 다른 이유: `cart-clear`는 화면당 하나 고정으로 존재하는 요소라 표시 여부만 토글하는 편이 단순하고, 할인 요소는 줄과 함께 매번 다시 그려지는 요소이기 때문이다. qa-agent는 이 차이대로 단언한다 (bug-history M2 참고 — "DOM에 있는지"와 "지금 보이는지"를 구분해서 단언할 것).
- **14.5** 할인이 적용된 줄의 `cart-item-price`(원래 단가)에는 취소선이 보여야 한다. 취소선은 CSS(`text-decoration: line-through`)로 처리하며, **할인 여부의 판정 근거는 취소선 스타일이 아니라 14.2 요소의 존재 여부**다 (스타일로 단언하면 CSS 변경마다 테스트가 깨진다).
- **14.6** 위 선택자를 추가하면서 10.10의 기존 4개(`cart-item-name`, `cart-item-price`, `cart-item-quantity`, `cart-item-total`)의 이름·위치·의미는 **바뀌지 않아야 한다.**

## 기능 요구사항 — 4차 사이클 추가분 (2026-08-10) · 모의 결제

아래 15~19장이 이번 사이클에 새로 구현할 범위다. **1~14장은 이미 구현·검증·커밋이 끝났으므로 회귀만 확인하고 다시 만들지 않는다** (단 7.10과 13.8은 위의 개정 노트를 반영한다).
신규 화면은 `/checkout.html`과 `/order.html` 2개이며, 기존 화면 중 변경 지점은 **장바구니 화면의 "결제하기" 링크 하나뿐**이다.

> 🔁 **이번 장 전체에 걸리는 대전제:** 여기서 말하는 "결제"는 **전부 모의 결제이며 외부 PG를 연동하지 않는다.** 문서 최상단 제약 블록의 "만들지 않는 것" 표가 15~19장 어디에도 예외 없이 적용된다.

### 15. 장바구니 → 결제 진입 (7.10 개정분)

- **15.1** 장바구니 화면에 **"결제하기" 링크**가 있어야 하며, 클릭하면 `/checkout.html`로 이동해야 한다. 이동 수단은 실제 `<a href="/checkout.html">` 링크여야 한다 (5.1과 같은 이유 — 새 탭 열기·뒤로가기가 브라우저 기본 동작으로 되어야 한다).
- **15.2** 장바구니가 비어 있으면(항목 0개) 이 링크는 **화면에 보이지 않아야 한다.** 요소는 DOM에 남기고 `hidden` 처리한다 — **11.5의 `cart-clear`와 완전히 같은 규칙**이다. 항목이 1개 이상이면 보여야 한다.
- **15.3 (진입점은 하나)** 결제 화면으로 들어가는 링크·버튼은 **장바구니 화면에만** 둔다. **상품 상세 화면의 "바로 구매"·"결제하기" 금지(6.12)는 그대로 유효하며**, 상품 목록 화면과 공통 헤더에도 결제 링크를 만들지 않는다. (D7에서 "담는 경로를 하나로 고정"한 것과 같은 판단 — 결제 경로가 둘이면 QA 경로도 둘이 된다)
- **15.4** 장바구니 화면의 나머지는 **하나도 바뀌지 않는다.** 줄 표시(7.1), 수량 변경(7.2~7.4), 삭제(7.5), 합계(7.6), 빈 상태(7.7), 비우기(11장), 할인 표시(12장), 기존 선택자(10.8~10.13 / 14.x)가 전부 그대로여야 한다. 이번에 추가되는 것은 링크 하나뿐이다.
- **15.5** 링크가 추가되면서 **비우기 버튼(`cart-clear`)의 위치나 동작이 바뀌면 안 된다.** 두 요소는 서로 독립이며, "결제하기"를 눌렀다고 장바구니가 비워지지 않는다 (비우기는 오직 11.1의 조작으로만).

### 16. 결제 화면 (`/checkout.html`) — 모의 결제

#### 16.1~16.5 — 주문 요약 (읽기 전용)

- **16.1** `/checkout.html`에 접속하면 `GET /api/cart`를 **한 번** 호출해 결제할 내용을 요약 표시해야 한다. 각 줄은 **상품명, 수량, 줄 합계(`lineTotal`)** 3가지를 표시하고, 요약 하단에 **총 수량(`totalQuantity`)과 총 금액(`totalPrice`)** 을 표시한다.

  > 이 화면은 `GET /api/cart` **한 번**으로 요약과 헤더 배지를 **둘 다** 채운다. 배지용으로 같은 API를 한 번 더 호출하지 않는다 — 페이지 로드 시 장바구니 API를 병렬로 여러 번 쏘는 패턴은 `docs/bug-history/2026-08-08_cart-session-race-condition.md`(M4)가 지목한 재발 조건이다.
- **16.2 (읽기 전용)** 주문 요약은 **읽기 전용이다.** 수량 증감 버튼·삭제 버튼·비우기 버튼을 **만들지 않으며**, 이 화면에서 `PATCH`/`DELETE` 계열 장바구니 API를 호출하지 않는다. 내용을 바꾸려면 장바구니 화면으로 돌아간다.
- **16.3** 결제 화면에는 **장바구니로 돌아가는 링크**가 있어야 한다 (6.11의 "목록으로 돌아가는 링크"와 같은 성격).
- **16.4 (금액은 서버 값 그대로)** 요약의 모든 금액은 응답의 `lineTotal`·`totalPrice`를 **그대로 포맷팅만 해서** 출력한다. 프론트가 `price × quantity`를 다시 계산하거나 합산하지 않는다 (7.6 / D12의 연장). **할인이 걸린 줄이 있어도 결제 화면의 총 금액은 장바구니 화면의 총 금액과 정확히 같아야 한다.**
- **16.5 (할인 UI 없음)** 결제 화면에는 **할인 UI(취소선 원가 / 할인 단가 / 할인 안내 문구)를 만들지 않는다.** 12.9의 3가지 표시는 **장바구니 화면 전용**이다. 결제 화면은 할인이 **이미 반영된 금액만** 보여준다. (표시 사양이 화면마다 한 벌씩 늘면 그중 하나만 어긋나고, 어느 화면이 정답인지 판정할 수 없게 된다 — D15와 같은 판단)

#### 16.6~16.7 — 입력 (최소 정보 + 모의 결제 수단)

- **16.6 (주문자 정보)** 아래 **2개 입력란만** 만든다.

  | 입력란 | 필드명 | 규칙 |
  |---|---|---|
  | 주문자 이름 | `ordererName` | 앞뒤 공백 제거 후 **1자 이상 30자 이하** |
  | 연락처 | `ordererPhone` | 휴대폰 번호. 하이픈 있는 형태와 없는 형태 **둘 다 허용** (정확한 규칙은 18.5) |

  **그 외 어떤 입력란도 만들지 않는다** — 배송지 주소·우편번호·상세주소·이메일·배송 요청사항·수령인, 그리고 **카드번호/유효기간/CVC/생년월일 등 실제 결제 정보 입력란 전부** (D18 / 최상단 제약 블록).
- **16.7 (모의 결제 수단)** 결제 수단은 **라디오 버튼 2개**이며, 이것이 결제 수단 UI의 **전부**다.

  | 값 (`paymentMethod`) | 화면 라벨 | 결과 |
  |---|---|---|
  | `MOCK_SUCCESS` | `모의 결제 (승인 성공)` | 승인 → 200 |
  | `MOCK_FAILURE` | `모의 결제 (승인 거절 — 실패 테스트용)` | 거절 → 402 |

  - **초기 선택값은 `MOCK_SUCCESS`** 다. 아무것도 선택되지 않은 상태로 화면이 뜨면 안 된다.
  - 이 두 값은 **모의 결제의 결과를 고르는 제어값**이지 실제 결제 수단(신용카드/계좌이체/간편결제)이 아니다. 카드사 선택·간편결제 로고 같은 것을 만들지 않는다.
  - 라벨 문구에 **"모의"와 "실패 테스트용"이 드러나야 한다** — 이 화면을 보는 사람이 실제 결제로 오해하면 안 된다.

#### 16.8~16.10 — 결제 요청

- **16.8** "결제하기" 버튼을 클릭하면 `POST /api/checkout`을 아래 body로 호출해야 한다.

  ```json
  { "ordererName": "홍길동", "ordererPhone": "010-1234-5678", "paymentMethod": "MOCK_SUCCESS" }
  ```

  **금액(`totalPrice`)·상품 목록(`items`)·수량을 body에 담지 않는다.** 결제 대상과 금액은 서버가 `cartId` 쿠키의 현재 장바구니에서 직접 계산한다 (18.1). 프론트가 금액을 보내면 계산 주체가 둘이 되고(D12 위반), 클라이언트가 보낸 금액을 서버가 믿는 구조가 된다.
- **16.9 (⚠️ 프론트가 결과를 미리 판정하지 않는다)** `MOCK_FAILURE`가 선택되어 있어도 프론트는 **반드시 서버에 요청을 보내고, 402 응답을 받아서** 실패를 표시해야 한다. `paymentMethod === 'MOCK_FAILURE'`인지 프론트에서 검사해 요청 없이 실패 화면을 그리면 **안 된다.** (12.11에서 프론트가 `quantity >= 10`을 다시 판정하지 못하게 한 것과 같은 규칙 — 판정은 서버에만 있다)
- **16.10 (이중 클릭 방지)** 결제 요청이 진행되는 동안 결제 버튼은 **비활성화(`disabled`)** 되어야 하고, 응답이 도착하면(성공·실패·에러 **모두**) 다시 활성화되어야 한다. 버튼을 빠르게 두 번 눌러도 `POST /api/checkout`이 두 번 나가면 안 된다. (실패 후 재시도를 막지 않기 위해, 실패 시에도 반드시 다시 활성화된다)

#### 16.11~16.16 — 응답 처리 (성공/실패 갈래)

- **16.11 (성공 — 200)** 승인에 성공하면 응답의 `order.orderId`를 사용해 **`/order.html?orderId={orderId}`로 이동해야 한다.** 결제 화면에 성공 메시지를 띄우고 머무르지 않는다.
- **16.12 (승인 거절 — 402)** 승인이 거절되면 **결제 화면에 그대로 머물며** 에러 영역(`checkout-error`)에 서버가 보낸 메시지를 표시해야 한다. 이때:
  - 입력한 주문자 이름·연락처가 **지워지지 않고 그대로 남아** 있어야 한다.
  - 주문 요약과 총 금액이 **그대로 유지**되어야 한다.
  - 결제 수단을 `MOCK_SUCCESS`로 바꿔 다시 "결제하기"를 누르면 **성공해야 한다.** (재시도 경로가 살아 있어야 한다 — 16.10)
  - **주문 확인 화면으로 이동하지 않는다.**
- **16.13 (입력 검증 실패 — 400)** 400 응답이면 에러 영역에 서버 메시지를 표시하고 **화면을 이동하지 않는다.**
- **16.14 (빈 장바구니 — 409)** 409 응답이면 에러 영역에 서버 메시지를 표시하고, **상품 목록으로 가는 링크**를 함께 보여준다. 화면을 이동하지 않는다.
- **16.15 (⚠️ 실패 시 장바구니 불변)** **결제가 성공하지 않은 모든 경우(400 / 402 / 409 / 5xx / 네트워크 오류)에 장바구니는 절대 비워지지 않아야 한다.** 실패 후 장바구니 화면으로 돌아가면 담긴 줄·수량·할인·총액이 **결제 시도 전과 완전히 동일**해야 한다. 프론트가 요청을 보내자마자 미리 장바구니를 비우거나 배지를 0으로 만드는 낙관적 갱신을 하면 안 된다 (11.6과 같은 규칙).
- **16.16 (빈 장바구니로 직접 접속)** 장바구니가 비어 있는 상태에서 `/checkout.html`에 직접 접속하면 빈 상태(`checkout-empty`)로 **"장바구니가 비어 있습니다" 같은 메시지 + 상품 목록으로 가는 링크**를 표시해야 한다. 이때 **주문자 입력 폼·결제 수단 라디오·결제하기 버튼은 화면에 보이지 않아야 한다** (빈 장바구니로 결제 요청을 보낼 수 있는 상태로 두지 않는다).

#### 16.17~16.20 — 상태·검증·헤더

- **16.17 (상태 배타성)** 결제 화면의 상태(**로딩 / 정상(요약+폼) / 빈 상태 / 에러**)는 서로 배타적이어야 한다 — 동시에 두 개 이상이 화면에 보이면 안 된다 (2.4 / 6.10 / 7.9와 같은 규칙).

  > 단 **16.12·16.13·16.14의 에러 표시는 예외다.** 이것들은 "화면 전체가 에러 상태"가 아니라 **정상 상태 위에 뜨는 요청 실패 안내**이므로, 주문 요약과 폼이 함께 보인 채로 `checkout-error`가 표시된다 (재시도하려면 폼이 보여야 하기 때문이다 — 16.12). "화면 전체 에러 상태"는 `GET /api/cart` 자체가 실패해 요약을 못 그리는 경우를 말한다.
- **16.18 (프론트 입력 검증 없음)** 프론트는 입력 검증을 **하지 않는다** (D25). 이름이 비어 있든 연락처 형식이 틀렸든 **일단 서버로 보내고, 400 응답의 메시지를 화면에 표시한다.** 또한 `required`·`pattern`·`minlength`·`maxlength` 등 **HTML5 기본 검증 속성을 쓰지 않는다** — 브라우저가 전송을 막으면 qa-agent가 400 케이스를 검증할 방법이 사라진다.
- **16.19 (헤더)** 결제 화면에도 5.4의 **공통 헤더(장바구니 링크 + 수량 배지)** 가 있어야 한다. 배지 값은 16.1의 `GET /api/cart` 응답의 `cart.totalQuantity`를 그대로 쓴다 (5.5 / 5.6).
- **16.20 (서버 에러 — 5xx / 네트워크)** 결제 요청이 5xx나 네트워크 오류로 실패하면 에러 메시지가 표시되어야 하며, 화면이 비거나 깨지면 안 된다. 이 경우에도 16.15(장바구니 불변)와 16.10(버튼 재활성화)이 그대로 적용된다.

### 17. 주문 확인 화면 (`/order.html?orderId={orderId}`)

- **17.1** `/order.html?orderId={orderId}`에 접속하면 `GET /api/orders/{orderId}`를 **한 번** 호출해 아래를 표시해야 한다.
  1. **주문번호** (`orderId`)
  2. **결제 상태** — "결제 완료" 같은 표시
  3. **주문 일시** (`createdAt`)
  4. **주문자 이름·연락처** (`ordererName`, `ordererPhone`)
  5. **주문 상품 줄들** — 각 줄에 상품명, 수량, 줄 합계(`lineTotal`)
  6. **총 수량·총 금액** (`totalQuantity`, `totalPrice`)
- **17.2 (상태 표시의 근거)** "결제 완료" 표시의 근거는 **응답의 `status` 값(`"PAID"`)** 이다. 프론트가 "여기까지 왔으면 성공"이라고 가정해 문구를 하드코딩하지 않는다 (12.11에서 `discountApplied` 하나로 판정하게 한 것과 같은 원칙).
- **17.3 (금액은 서버 값 그대로)** 모든 금액은 응답 값을 **그대로 포맷팅만 해서** 출력한다. 프론트가 재계산·재합산하지 않는다 (16.4와 같은 규칙).
- **17.4 (금액 일치 — 핵심 검증)** 주문의 `totalPrice`는 **결제 직전 장바구니의 `totalPrice`와 정확히 같아야 한다.** 할인이 걸린 줄이 있어도 마찬가지다. 즉 **장바구니 총액 == 결제 화면 총액 == 주문 확인 총액** 세 값이 항상 일치해야 한다.
- **17.5 (새로고침 유지)** 주문 확인 화면을 **새로고침(F5)해도 주문 정보가 그대로 표시되어야 한다.** (서버에서 다시 조회하므로 — D22). 결제 응답을 메모리에만 들고 있다가 새로고침에 잃는 구현이면 안 된다.
- **17.6 (`orderId` 없음)** `?orderId=`가 아예 없거나 빈 문자열이면 **API를 호출하지 않고** 곧바로 not-found 상태를 표시해야 한다 (6.9와 같은 규칙).
- **17.7 (없는 주문 — 404)** 존재하지 않는 `orderId`로 접속하면 **"주문을 찾을 수 없습니다" 같은 not-found 상태**와 상품 목록으로 가는 링크가 표시되어야 한다. 빈 화면이나 깨진 화면이 되면 안 된다 (6.8과 같은 규칙).
- **17.8 (⚠️ 남의 주문은 보이지 않는다)** **다른 브라우저나 시크릿 창에서 같은 주문 URL을 열면 not-found(404) 상태여야 한다.** 주문을 만든 브라우저에서만 보인다 (D23 / 8.5의 "브라우저별 분리"가 주문에도 이어진다). 프론트는 이 경우를 17.7과 **같은 화면**으로 처리한다 — "권한 없음" 전용 화면을 따로 만들지 않는다.
- **17.9 (링크)** 주문 확인 화면에는 **상품 목록으로 돌아가는 링크**가 있어야 하고, 5.4의 **공통 헤더(장바구니 링크 + 수량 배지)** 도 있어야 한다.
- **17.10 (배지 0)** 결제 성공으로 장바구니가 비워졌으므로(D19), 주문 확인 화면의 수량 배지는 **0이 되어 숨겨져 있어야 한다** (5.5). 배지를 채우기 위해 `GET /api/cart`를 호출해도 되지만, 그 호출이 실패하더라도 **주문 정보 렌더링은 정상적으로 되어야 한다** (5.7과 같은 규칙 — 배지만 숨긴다).
- **17.11 (상태 배타성)** 주문 확인 화면의 상태(**로딩 / 정상 / not-found / 에러**)는 서로 배타적이어야 한다 (6.10과 같은 규칙).
- **17.12 (할인 UI 없음)** 주문 확인 화면에도 **할인 UI를 만들지 않는다** (16.5와 같음). 할인이 반영된 금액만 표시한다.
- **17.13 (만들지 않는 버튼)** 주문 확인 화면에 **주문 취소·환불 요청·재주문·영수증 출력·배송 조회 버튼을 만들지 않는다.** 전부 Out of scope다.

### 18. API — 4차 추가분

기존 7개 엔드포인트의 **경로·메서드·응답 shape은 하나도 바뀌지 않는다.** 아래 2개가 추가된다.

| # | Method | Path | 역할 |
|---|---|---|---|
| 18.1 | POST | `/api/checkout` | 모의 결제 요청 (**신규**) |
| 18.9 | GET | `/api/orders/:orderId` | 주문 1건 조회 (**신규**) |

#### 18.1~18.8 — `POST /api/checkout`

- **18.1 (요청 body)** `POST /api/checkout`은 `{ "ordererName": string, "ordererPhone": string, "paymentMethod": string }` **3개 필드만** 받는다. **`items`·`totalPrice`·`quantity` 등 상품·금액 정보는 받지 않으며, body에 실려 오더라도 전부 무시한다.** 결제 대상과 금액은 서버가 `cartId` 쿠키의 **현재 장바구니에서 직접 계산**한다 (`buildCartSnapshot()` 재사용 — 12.5의 할인 계산이 그대로 적용된다).
- **18.2 (성공 응답)** 승인 성공 시 **200**과 함께 **`{ "order": { ... } }`** 를 반환한다. `order`의 필드는 데이터 모델의 `Order` 표 그대로다. **주문 객체를 top-level로 그대로 반환하지 않는다** (3.1 / 9.1의 래핑 원칙과 동일).
- **18.3 (⚠️ 모의 결제 판정 — 결정론)** 승인/거절 판정은 **서버가 요청의 `paymentMethod` 값만으로 결정론적으로** 한다.

  ```
  paymentMethod === "MOCK_SUCCESS"  →  승인  (200)
  paymentMethod === "MOCK_FAILURE"  →  거절  (402)
  그 외 값                            →  검증 실패 (400, 18.5)
  ```

  - **난수(`Math.random()`), 확률, 시각(초/밀리초), 주문 금액, 주문자 이름 등 어떤 것도 판정에 쓰지 않는다** (D17). 같은 입력이면 **몇 번을 호출해도 같은 결과**여야 한다.
  - **외부 PG API를 호출하지 않는다.** 네트워크 요청 없이 서버 안에서 즉시 판정한다.
  - 승인 처리를 지연시키는 인위적 `setTimeout`/`sleep`을 넣지 않는다 (QA 실행 시간만 늘고 얻는 게 없다).
- **18.4 (승인 거절 응답)** 거절 시 **402 Payment Required**와 `{ "error": { "message": "결제가 승인되지 않았습니다. 다른 결제 수단으로 다시 시도해 주세요." } }`를 반환한다. 이때:
  - **장바구니를 비우지 않는다.**
  - **주문을 저장하지 않는다** (D21). `orderId`도 발급하지 않는다.
  - **200에 `{ "order": { "status": "FAILED" } }`를 담아 보내지 않는다** (D24 / 9.13).
- **18.5 (검증 실패 — 400)** 아래 경우 **400**과 `{ "error": { "message": "..." } }`를 반환한다.

  | 대상 | 400이 되는 조건 | 권장 메시지 |
  |---|---|---|
  | `ordererName` | 없음 / 문자열 아님 / **앞뒤 공백 제거 후** 1자 미만(빈 문자열·공백만) 또는 **30자 초과** | `주문자 이름을 1자 이상 30자 이하로 입력해 주세요.` |
  | `ordererPhone` | 없음 / 문자열 아님 / **앞뒤 공백 제거 후** 정규식 `^(01\d-\d{3,4}-\d{4}\|01\d\d{7,8})$` 불일치 | `연락처를 올바른 휴대폰 번호 형식으로 입력해 주세요.` |
  | `paymentMethod` | 없음 / `"MOCK_SUCCESS"`·`"MOCK_FAILURE"` 둘 중 하나가 아님 | `결제 수단을 선택해 주세요.` |

  연락처 정규식은 표 안에서 파이프 문자가 이스케이프되어 있으므로, **아래 코드 블록이 정확한 확정값**이다.

  ```js
  const ORDERER_PHONE_PATTERN = /^(01\d-\d{3,4}-\d{4}|01\d\d{7,8})$/;
  // 하이픈이 전부 있거나(010-1234-5678), 전부 없거나(01012345678) 둘 중 하나만 허용.
  // 하이픈이 섞인 형태(010-12345678)는 불허 — 허용 형태를 둘로 고정해야 QA 케이스가 유한해진다.
  ```

  - 연락처 **허용 예**: `010-1234-5678`, `01012345678`, `010-123-4567`, `0101234567`
  - 연락처 **불허 예**: `010-1234-567`(끝자리 부족), `02-123-4567`(휴대폰 아님), `010-12345678`(하이픈 혼용), `010 1234 5678`(공백 구분), `abc`, `""`(빈 문자열), `"   "`(공백만)
  - 검증은 **저장 전에** 끝낸다. 검증 실패 시 장바구니를 비우지 않고 주문도 만들지 않는다.
  - **검증 순서: 입력 검증(400) → 빈 장바구니(409) → 승인 판정(402).** 입력이 틀렸는데 승인 판정부터 하면 400이어야 할 요청이 402로 나간다.
- **18.6 (빈 장바구니 — 409)** 현재 `cartId`의 장바구니가 비어 있으면(줄 0개) **409 Conflict**와 `{ "error": { "message": "장바구니가 비어 있어 결제할 수 없습니다." } }`를 반환한다. **400이 아닌 이유:** 요청 body 자체는 올바르고 서버 상태와의 충돌이므로, 프론트가 "입력을 고치세요"가 아니라 "장바구니에 상품을 담으세요"라는 다른 안내를 띄워야 한다 (D24 / 16.14).
- **18.7 (성공 시 부수 효과 — 한 요청 안에서)** 승인 성공 시 서버는 **같은 요청 처리 안에서** 아래를 모두 끝낸다.
  1. 주문을 `Map<orderId, Order>`에 저장한다 (주문 시점의 장바구니 스냅샷을 **복사해서** 담는다 — 나중에 장바구니가 비워져도 주문 내용이 남아야 한다).
  2. **해당 `cartId`의 장바구니를 비운다** (D19).
  3. 저장된 주문을 200으로 반환한다.

  **프론트가 `DELETE /api/cart`를 별도로 호출하지 않는다.** 또한 주문의 `items`는 장바구니 배열을 **참조로 공유하면 안 된다** — 장바구니를 비우는 순간 주문 내용까지 비워지는 버그가 난다. 반드시 복사본을 저장한다.
- **18.8 (재고)** **재고를 차감하지 않는다.** `Product`에 재고 필드를 추가하지 않고, 품절·재고 부족으로 인한 결제 실패 케이스도 만들지 않는다 (D20). 결제 실패 사유는 18.4의 모의 승인 거절 **하나뿐**이다.

#### 18.9~18.11 — `GET /api/orders/:orderId`

- **18.9 (조회 성공)** `GET /api/orders/:orderId`는 해당 주문이 존재하고 **요청의 `cartId` 쿠키가 그 주문을 만든 `cartId`와 같으면** 200과 함께 `{ "order": { ... } }`를 반환한다. 응답의 `order` shape은 18.2와 **완전히 동일**하다 (프론트가 결제 응답과 조회 응답을 같은 렌더 함수로 처리할 수 있어야 한다 — 9.7과 같은 원칙).
- **18.10 (404 — 두 경우를 같게 처리)** 아래 **두 경우 모두** 404와 `{ "error": { "message": "주문을 찾을 수 없습니다." } }`를 반환한다. **메시지도 상태 코드도 구분하지 않는다.**
  1. `orderId`가 존재하지 않을 때
  2. 존재하지만 요청의 `cartId` 쿠키가 주문의 `cartId`와 **다를 때** (쿠키가 아예 없는 경우 포함)

  **403이 아니라 404다** (D23). 주문의 존재 여부 자체를 남에게 알리지 않고, 프론트 분기도 하나로 끝난다.
- **18.11 (주문 목록 없음)** `GET /api/orders`(복수형, 목록 조회)는 **만들지 않는다.** 단건 조회만 이번 범위다.

#### 18.12~18.16 — 공통 규격

- **18.12 (⚠️ 에러 메시지 — M5 재발 지점)** `/api/checkout`과 `/api/orders`에서 예상치 못한 500이 발생하면, **"상품 목록을 불러오지 못했습니다"가 아니라 결제·주문 문맥의 문구**가 나가야 한다.

  `docs/bug-history/2026-08-08_generic-error-message-leak.md`(BUG-2026-08-08-02, M5)가 **결제 API를 이름으로 지목해 예고한 재발 지점**이다. 현재 공용 핸들러는 `/api/products`와 `/api/cart`만 분기하고 있으므로, **분기를 추가하지 않으면 결제 실패 화면에 "상품 목록을 불러오지 못했습니다"가 그대로 뜬다.** 권장 문구: `결제 요청을 처리하지 못했습니다.` / `주문 정보를 불러오지 못했습니다.`
- **18.13 (범위 제한 — 13.8 개정판)** 이번 사이클의 API는 3차까지의 7개 + 위 2개 = **총 9개가 전부다.** 아래는 **만들지 않는다.**
  - **실제 PG 연동 관련 전부** — 결제 승인 API 호출, 웹훅 수신 엔드포인트, `returnUrl`/`successUrl`/`failUrl` 콜백 라우트, 결제창 리다이렉트 (최상단 제약 블록)
  - `GET /api/orders` (주문 **목록** 조회)
  - 주문 취소 / 환불 / 부분 취소 (`POST /api/orders/:orderId/cancel` 등)
  - 결제 수단 저장·관리, 영수증·현금영수증 발급
  - 배송지·배송비·배송 상태 관련 엔드포인트 전부
  - 쿠폰/프로모션 코드 (3차부터 그대로 범위 밖)
- **18.14 (에러 shape 불변)** 모든 에러 응답은 기존과 동일한 `{ "error": { "message": "..." } }`이며, `code` 같은 필드를 추가하지 않는다. **에러를 200으로 반환하면서 body로만 표시하면 안 된다** (9.13). 4차에서 새로 등장하는 상태 코드는 **402**(승인 거절)와 **409**(빈 장바구니) 두 개이며, body shape은 그대로다.
- **18.15 (쿠키)** 결제·주문 엔드포인트도 9.11의 쿠키 규칙을 그대로 따른다 (`Path=/`, `HttpOnly`, `SameSite=Lax`, `Max-Age=604800`, `Secure` 없음). 단 `POST /api/checkout`에 쿠키가 없는 상태로 들어오면 그 브라우저는 장바구니가 비어 있는 것이므로 쿠키를 발급하되 **18.6의 409**가 된다.
- **18.16 (멱등하지 않음 — 중복 주문 방지)** `POST /api/checkout`은 **멱등하지 않다.** 같은 body로 연속 두 번 호출하면 첫 번째는 200, 두 번째는 **409**(장바구니가 이미 비워졌으므로)가 된다. 이는 **의도된 동작이며 중복 주문 방지 장치를 겸한다** — 별도의 멱등 키(idempotency key)나 중복 요청 차단 로직을 추가로 만들지 않는다. (프론트 쪽 방어는 16.10의 버튼 비활성화가 담당한다)

- **19.11** 주문 정보 컨테이너에 `data-testid="order-confirmation"`과 `data-order-id="{orderId}"`가 있어야 한다 (10.3의 `product-detail`과 같은 형태).
- **19.12** 내부 요소에 각각 `data-testid="order-id"`, `data-testid="order-status"`, `data-testid="order-created-at"`, `data-testid="order-orderer-name"`, `data-testid="order-orderer-phone"`이 있어야 한다.
- **19.13** `order-created-at` 요소는 `<time>` 태그로 만들고 **`datetime` 속성에 응답의 `createdAt` 원본(ISO 8601 문자열)을 그대로 담는다.** 화면에 보이는 텍스트의 표기 형식은 frontend-agent 재량이다 — qa-agent는 `datetime` 속성으로 단언한다 (로케일 표기에 테스트를 묶지 않기 위함이며, 14.5에서 "취소선 스타일로 단언하지 말라"고 한 것과 같은 계열의 판단).
- **19.14** 주문 상품 줄 목록 컨테이너에 `data-testid="order-list"`, 각 줄에 `data-testid="order-item"`과 `data-product-id="{productId}"`가 있어야 한다.
- **19.15** 줄 내부 요소에 각각 `data-testid="order-item-name"`, `data-testid="order-item-quantity"`, `data-testid="order-item-total"`이 있어야 한다.
- **19.16** 합계에 `data-testid="order-total-quantity"`, `data-testid="order-total-price"`가 있어야 한다.
- **19.17** 주문 확인 화면의 상태 요소에 각각 `data-testid="order-loading"`, `data-testid="order-not-found"`, `data-testid="order-error"`가 있어야 한다. **17.7(없는 주문)과 17.8(남의 주문)은 둘 다 `order-not-found`로 표시된다** — 구분하지 않는다 (D23).

**존재/부재 규칙 (M2 대응)**

- **19.18** 이번에 추가되는 선택자 중 **`checkout-link`만 "DOM에 남기고 `hidden` 토글"** 이고, **나머지 목록 줄 요소(`checkout-item`, `order-item`)는 데이터가 없으면 DOM에 아예 존재하지 않는다.** 14.4의 할인 요소와 같은 이유로, 줄은 응답을 받을 때마다 다시 그려지므로 부재가 자연스럽고 qa-agent가 **요소 개수로 줄 수를 셀 수 있다.**

  > qa-agent는 이 차이대로 단언한다 — `checkout-link`는 `toBeHidden()`/`toBeVisible()`, `checkout-item`·`order-item`은 `toHaveCount(n)`. (`docs/bug-history/2026-08-05_and_08_minor-notes.md` M2 참고)
- **19.19** 위 선택자를 추가하면서 **기존 선택자(4.x / 10.x / 14.x)의 이름·위치·의미는 하나도 바뀌지 않아야 한다.**

> 선택자 이름은 **확정값**이다. frontend-agent가 임의로 바꾸면 qa-agent의 검증이 전부 실패한다. 바꿔야 하면 product-planner에게 먼저 문의한다.

| 필드 네이밍 컨벤션 | **camelCase** (`imageUrl`) | JSON/JS 생태계 표준이고, 아래 권장 스택(Node + 브라우저 JS)에서 서버·클라이언트가 변환 없이 같은 이름을 쓸 수 있음. snake_case를 쓰면 한쪽에서 반드시 변환 레이어가 생기고, 그 지점이 경계면 버그가 됨 |

| 목록 응답 래핑 | **`{ "items": [...] }`로 래핑** | 나중에 페이지네이션(`total`, `page`)이 필요해질 때 top-level 배열이면 응답 shape을 통째로 깨야 함. 지금 래핑해두면 확장 시 프론트 코드가 안 깨짐 |
| 식별자 타입 | **문자열(string)**, 예: `"p1"` | 시드 데이터 기준. 나중에 DB로 옮겨도 문자열이면 UUID/숫자 어느 쪽이든 흡수 가능 |

| 단건 응답 래핑 | **`{ "item": {...} }`로 래핑** (2차 추가) | 목록의 `items` 래핑과 같은 원칙. top-level에 payload를 그대로 두지 않으면 나중에 형제 키를 붙일 때 응답 shape이 깨지지 않는다 |
| 장바구니 응답 래핑 | **`{ "cart": {...} }`로 래핑** (2차 추가) | 위와 동일. 또한 조회/담기/변경/삭제 **4개 엔드포인트가 전부 같은 shape**을 반환하므로 프론트의 렌더 함수가 하나로 끝난다 (9.7) |
| 금액 계산 주체 | **서버** (`lineTotal`, `totalQuantity`, `totalPrice`를 응답에 포함) (2차 추가) → **3차에서 할인 필드 5개가 추가되어 총 8개** (13.7) | 합산 로직이 서버·프론트 두 곳에 있으면 값이 어긋났을 때 어느 쪽이 정답인지 판정할 수 없다 (9.8). **할인 계산도 예외가 아니다** (D12) |
| 할인 필드 네이밍 | **camelCase 유지.** `lineSubtotal`(할인 전) / `lineTotal`(할인 후) / `discountedUnitPrice` / `discountAmount` / `discountApplied` / `discountPercent` (3차 추가) | 기존 `lineTotal`을 "최종 금액"으로 **고정**하고 할인 전 금액에 새 이름(`lineSubtotal`)을 준다. 반대로 했다면(= `lineTotal`을 할인 전으로 두고 `lineFinal`을 신설) 2차에서 이미 `lineTotal`을 화면에 그리던 코드가 **소리 없이 할인 전 금액을 표시하게 된다.** "기존 필드가 계속 화면에 쓰이는 값이어야 한다"는 기준으로 정했다 |
| 할인 미적용 줄의 필드 값 | **필드는 항상 존재하고, `null` 금지.** `discountApplied: false`, `discountPercent: 0`, `discountAmount: 0`, `discountedUnitPrice: price`, `lineSubtotal: lineTotal` (3차 추가) | 줄마다 필드 유무가 달라지면 프론트에 `undefined` 분기가 생기고, 그 분기가 곧 버그 지점이 된다. **`discountedUnitPrice`를 미적용 시 `price`와 같게 두면** 화면이 "언제나 `discountedUnitPrice`를 단가로 그린다"는 한 갈래 로직으로도 정답이 나온다 (분기는 오직 할인 UI 표시 여부에만 필요 — 12.11) |
| 장바구니 단위 할인 요약 | **없음.** `cart`에 `totalDiscount` / `totalSubtotal` 같은 필드를 **추가하지 않는다** (3차) | 이번에 확정된 표시 사양은 **줄 단위 표시뿐**이다(12.9). 화면에 안 쓰는 필드를 응답에 넣으면 backend/frontend가 각자 다른 의미로 채워넣기 시작한다. 장바구니 단위 할인 요약이 필요해지면 그때 요구사항으로 추가한다 |
| 주문 응답 래핑 | **`{ "order": {...} }`로 래핑** (4차 추가) | `items`/`item`/`cart` 래핑과 같은 원칙. `POST /api/checkout`과 `GET /api/orders/:orderId` **두 엔드포인트가 같은 shape**을 반환하므로 프론트가 렌더 함수 하나로 처리한다 (18.9) |
| **enum 값의 표기** | **필드명은 camelCase, 값(enum)은 `UPPER_SNAKE_CASE`** — `status: "PAID"`, `paymentMethod: "MOCK_SUCCESS"` (4차 확정) | 필드명 컨벤션과 값 컨벤션은 별개다. enum 값을 대문자로 두면 화면에 그대로 노출할 문자열이 아님이 한눈에 보여, frontend-agent가 `status`를 그대로 출력하는 대신 표시 문구로 변환하게 된다. 또 `"paid"`/`"Paid"`/`"PAID"` 사이의 대소문자 흔들림이 원천적으로 없어진다 |
| 주문 상품 줄의 필드 구성 | **`CartItem`과 완전히 동일한 11개 필드를 그대로 복사한다.** `OrderItem`이라는 **별도 타입을 만들지 않는다** (4차 확정) | 필드 집합이 다르면 프론트가 장바구니 렌더 로직을 재사용할 수 없고, "주문 줄에는 어떤 필드가 있더라?"를 매번 확인해야 한다. 필드를 골라 담아 얻는 이득(응답 크기)보다, 두 벌의 shape을 유지하는 비용이 훨씬 크다. **할인 필드도 그대로 복사**되므로 주문 시점의 할인 내역이 스냅샷으로 남는다 |
| 결제 금액을 요청에서 받는지 | **받지 않는다.** `POST /api/checkout` body에 금액·상품 정보를 담지 않으며, 실려 와도 무시한다 (4차 확정) | D12("금액 계산 주체는 서버")의 직접적 연장. 클라이언트가 보낸 금액을 서버가 신뢰하는 구조를 만들지 않는다. 서버는 언제나 `cartId` 쿠키의 현재 장바구니에서 다시 계산한다 (18.1) |

### CartItem (2차 추가 / **3차에서 할인 필드 5개 추가**) — 장바구니의 한 줄

**서버가 응답에 담아 내려주는 형태**다. 서버 내부 저장은 `{ productId, quantity }`만 들고 있어도 되지만, **응답에는 아래 11개 필드를 모두 채워서 내려야 한다.** (2차의 6개 + 3차의 5개)

| 필드 | 타입 | 필수 | 사이클 | 설명 |
|---|---|---|---|---|
| `productId` | string | O | 2차 | 상품 `id`와 같은 값(`"p1"`). **이 값이 곧 줄의 식별자다** (D8). `id`라는 이름을 쓰지 않는다 — 장바구니 줄과 상품을 헷갈리지 않게 하기 위함 |
| `name` | string | O | 2차 | 상품명. Product에서 복사해 넣는다 |
| `price` | integer | O | 2차 | **원래 단가**(원 단위 정수). Product의 `price`와 같은 값. 할인이 적용되어도 **이 값은 깎이지 않는다** — 화면에서 취소선 쳐서 보여줄 원가다 (12.9-1 / 10.10) |
| `imageUrl` | string | O | 2차 | 상품 이미지 URL. Product에서 복사 |
| `quantity` | integer | O | 2차 | 담긴 수량. **1 이상 99 이하 정수** |
| `lineSubtotal` | integer | O | **3차** | **할인 전** 줄 금액 = `price × quantity`. (2차까지 `lineTotal`이 담던 값이 이 필드로 옮겨왔다) |
| `discountApplied` | boolean | O | **3차** | 이 줄에 할인이 적용됐는지. `quantity >= 10`이면 `true`, 아니면 `false` (12.2). **화면의 할인 UI 표시 여부는 오직 이 필드로 판정한다** (12.11). 미적용 줄에서도 `false`를 **반드시 채운다** (생략·`null` 금지) |
| `discountPercent` | integer | O | **3차** | 적용된 할인율(정수 퍼센트). 적용 시 `10`, 미적용 시 **`0`**. 안내 문구의 숫자로 쓴다 (12.15). `0.1` 같은 비율(rate)이 아니라 **퍼센트 정수**다 |
| `discountedUnitPrice` | integer | O | **3차** | **실제로 적용되는 단가.** 적용 시 `price - floor(price × 10 / 100)` (예: `19000` → `17100`), **미적용 시 `price`와 같은 값**. 화면의 할인가 자리에 그대로 출력한다 (14.2) |
| `discountAmount` | integer | O | **3차** | 이 줄에서 깎인 금액 = `lineSubtotal - lineTotal`. 미적용 시 **`0`**. 응답에는 **항상 포함**하되, 화면 표시 여부는 frontend-agent 재량이다(전용 선택자를 두지 않았다 — 확정된 표시 사양은 12.9의 3가지뿐) |
| `lineTotal` | integer | O | 2차(**3차에서 의미 변경**) | **할인 후 최종 줄 금액** = `discountedUnitPrice × quantity`. 화면의 줄 합계(`cart-item-total`)와 `totalPrice` 합산에 쓰이는 값은 **전부 이 필드**다. ⚠️ 2차의 정의(`price × quantity`)는 폐기됐다 (9.8 개정) |

> **불변식 (qa-agent 검증용).** 모든 줄에서 아래가 성립해야 한다.
> - `lineSubtotal == price * quantity`
> - `lineTotal == discountedUnitPrice * quantity`
> - `discountAmount == lineSubtotal - lineTotal`
> - `discountApplied == (quantity >= 10)`
> - `discountApplied == false` 이면 → `discountPercent == 0` 이고 `discountAmount == 0` 이고 `discountedUnitPrice == price` 이고 `lineTotal == lineSubtotal`
> - 모든 금액 필드는 **정수**다. 소수가 나오면 12.5의 버림 규칙을 안 지킨 것이다.

> `name` / `price` / `imageUrl`을 장바구니 응답에 **일부러 중복해서 담는다.** 이렇게 하지 않으면 장바구니 화면이 줄마다 `GET /api/products/:id`를 따로 호출해야 하고, 그 N+1 호출이 새로운 실패 지점이 된다. 상품 데이터가 시드라서 갱신 문제도 없다.
>
> CartItem에 `description`은 담지 않는다 (장바구니에서 쓰지 않음).

### Cart (2차 추가) — 장바구니 스냅샷

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `items` | CartItem[] | O | 담긴 줄 배열. 비어 있으면 `[]` (`null` 금지). 순서는 **처음 담은 순서(추가된 순)** 를 유지한다 — 수량을 바꿔도, 할인이 켜지고 꺼져도 줄 위치가 튀면 안 된다 |
| `totalQuantity` | integer | O | 모든 줄의 `quantity` 합. 서버 계산. **할인과 무관하다** (할인이 수량을 바꾸지 않는다 — 12.6) |
| `totalPrice` | integer | O | 모든 줄의 `lineTotal` 합. 원 단위 정수. 서버 계산. **3차부터 `lineTotal`이 할인 후 금액이므로 이 값은 곧 "할인이 반영된 총 금액"이다** (12.6). `lineSubtotal`의 합이 **아니다** |

> **Cart에는 할인 요약 필드를 두지 않는다.** `totalDiscount`, `totalSubtotal`, `discountedItemCount` 같은 필드를 임의로 추가하지 않는다 — 이번 사이클에 확정된 표시 사양은 줄 단위뿐이다(위 네이밍 규칙 표 참고). 필요해지면 요구사항으로 먼저 추가한다.

### Order (4차 추가) — 주문 (모의 결제 성공 시에만 생성된다)

**승인에 성공한 결제만 `Order`가 된다.** 승인 거절(402)·검증 실패(400)·빈 장바구니(409)에서는 주문이 **만들어지지도 저장되지도 않는다** (D21 / 18.4).

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `orderId` | string | O | **주문번호이자 조회 키.** 형식 **`ORD-YYYYMMDD-XXXXXX`** — `YYYYMMDD`는 **UTC 기준** 생성일, `XXXXXX`는 대문자 영문+숫자(`[A-Z0-9]`) 6자리. 예: `"ORD-20260810-K3F9A2"`. 정규식: `^ORD-\d{8}-[A-Z0-9]{6}$`. 생성 시 이미 존재하는 키면 **다시 생성**한다 |
| `status` | string | O | 결제 상태. **값은 `"PAID"` 하나뿐이다** (저장되는 주문은 전부 승인 성공분이므로 — D21). 화면의 "결제 완료" 표시는 이 필드를 근거로 그린다 (17.2). `"FAILED"`·`"PENDING"`·`"CANCELLED"` 같은 값은 이번 범위에 **존재하지 않는다** |
| `ordererName` | string | O | 주문자 이름. 요청 값을 **앞뒤 공백만 제거(trim)** 해서 저장한다. 1~30자 (18.5) |
| `ordererPhone` | string | O | 주문자 연락처. 요청 값을 **앞뒤 공백만 제거해서 그대로** 저장한다. **하이픈을 제거하거나 형식을 재조립하지 않는다** — 입력한 그대로 저장하고 그대로 반환해야 화면 표기가 서버·클라이언트 사이에서 흔들리지 않는다 |
| `paymentMethod` | string | O | 모의 결제 수단. `"MOCK_SUCCESS"` 또는 `"MOCK_FAILURE"`. **저장되는 주문에는 사실상 `"MOCK_SUCCESS"`만 들어간다** (`MOCK_FAILURE`는 402로 끝나 저장되지 않으므로). 필드를 남기는 이유는 "어떤 수단으로 결제했는가"가 주문의 속성이고, qa-agent가 이 값으로 불변식을 단언할 수 있기 때문이다 |
| `items` | CartItem[] | O | **주문 시점 장바구니 줄들의 복사본.** 각 요소는 `CartItem`과 **완전히 동일한 11개 필드**를 갖는다 (할인 필드 5개 포함). 빈 배열일 수 없다 — 비어 있으면 애초에 409다 (18.6). ⚠️ **장바구니 배열을 참조로 공유하지 말고 복사한다** (18.7) |
| `totalQuantity` | integer | O | 주문 시점 `cart.totalQuantity`의 복사본. 모든 줄의 `quantity` 합 |
| `totalPrice` | integer | O | **실제 결제된 금액.** 주문 시점 `cart.totalPrice`의 복사본이며 **할인이 반영된 `lineTotal`들의 합**이다 (12.6). 원 단위 정수 |
| `createdAt` | string | O | 주문 생성 시각. **ISO 8601 UTC 문자열** (`new Date().toISOString()`), 예: `"2026-08-10T04:12:33.512Z"`. 화면 표기 형식은 frontend-agent 재량이되, `<time datetime="...">`에 이 원본을 담는다 (19.13) |

> **⚠️ 응답에 담지 않는 서버 내부 필드**
>
> 서버는 주문마다 **어느 장바구니에서 만들어졌는지(`cartId`)를 함께 보관**해야 한다 (18.9의 소유자 판정에 쓰인다 — D23). 하지만 이 값은 **응답에 절대 포함하지 않는다.** `cartId`는 `HttpOnly` 쿠키로만 다뤄지는 값이고(8.6), 응답 body로 내보내면 프론트가 읽을 수 있게 되어 8.6이 깨진다.
>
> 즉 서버 저장 구조는 `Map<orderId, { ...위 9개 필드, cartId }>`이고, **응답으로 나가는 `order`는 위 표의 9개 필드뿐이다.**

> **불변식 (qa-agent 검증용).** 저장되어 조회되는 모든 주문에서 아래가 성립해야 한다.
> - `status === "PAID"` (다른 값은 존재하지 않는다)
> - `orderId`가 `^ORD-\d{8}-[A-Z0-9]{6}$`에 일치한다
> - `items.length >= 1`
> - `totalQuantity === items`의 `quantity` 합
> - `totalPrice === items`의 `lineTotal` 합 (**`lineSubtotal` 합이 아니다** — 할인 반영분)
> - `totalPrice`가 **결제 직전 장바구니의 `totalPrice`와 정확히 같다** (17.4)
> - 각 줄이 `CartItem`의 불변식 6개를 그대로 만족한다 (`lineTotal === discountedUnitPrice * quantity` 등)
> - 모든 금액 필드가 **정수**다
> - 결제 성공 직후 `GET /api/cart`는 **빈 장바구니**를 반환한다 (D19 / 18.7)

### API 응답 shape — 3차 추가분 (확정, **장바구니 엔드포인트 5개의 최종 기준이다**)

> ℹ️ **[4차 보강 — 2026-08-10]** 아래 블록은 **장바구니를 반환하는 5개 엔드포인트의 최종 기준으로 그대로 유효하다.** 4차에서 추가되는 결제·주문 엔드포인트 2개의 shape은 아래 "4차 추가분" 블록에 있다. `CartItem` 11개 필드는 **주문(`order.items`)에서도 그대로 쓰인다.**

```
DELETE /api/cart                     →  200   (신규 — 전체 비우기, 13.1)
{ "cart": { "items": [], "totalQuantity": 0, "totalPrice": 0 } }

  이미 비어 있어도 같은 응답 (멱등 — 13.2). 404/400 아님.


장바구니를 반환하는 5개 엔드포인트(GET /api/cart, POST /api/cart/items,
PATCH /api/cart/items/:productId, DELETE /api/cart/items/:productId, DELETE /api/cart)는
모두 아래 shape을 반환한다 (13.5). CartItem 필드는 11개이며 하나도 생략하지 않는다 (13.6).

{
  "cart": {
    "items": [
      {
        "productId": "p1",
        "name": "베이직 코튼 티셔츠",
        "price": 19000,
        "imageUrl": "/images/p1.svg",
        "quantity": 10,
        "lineSubtotal": 190000,
        "discountApplied": true,
        "discountPercent": 10,
        "discountedUnitPrice": 17100,
        "discountAmount": 19000,
        "lineTotal": 171000
      },
      {
        "productId": "p7",
        "name": "러닝 스니커즈",
        "price": 89000,
        "imageUrl": "/images/p7.svg",
        "quantity": 1,
        "lineSubtotal": 89000,
        "discountApplied": false,
        "discountPercent": 0,
        "discountedUnitPrice": 89000,
        "discountAmount": 0,
        "lineTotal": 89000
      }
    ],
    "totalQuantity": 11,
    "totalPrice": 260000
  }
}

  위 예시 검산:
    p1 줄 — 할인 O: 19000 - floor(19000*10/100)=19000-1900=17100 → 17100 * 10 = 171000
    p7 줄 — 할인 X: 단가 그대로 89000 → 89000 * 1 = 89000
    totalQuantity = 10 + 1 = 11        (할인과 무관)
    totalPrice    = 171000 + 89000 = 260000   (할인 후 lineTotal들의 합 — 12.6)
                    ※ 할인 전 합(190000+89000=279000)이 아니다

  경계값 예시 (12.2) — 같은 상품 수량만 9로 바꾸면:
    { ..., "quantity": 9, "lineSubtotal": 171000, "discountApplied": false,
      "discountPercent": 0, "discountedUnitPrice": 19000, "discountAmount": 0,
      "lineTotal": 171000 }
    ※ 9개일 때의 lineTotal(171,000원)과 10개일 때의 lineTotal(171,000원)이 우연히 같다.
      "1개 더 담았는데 총액이 그대로"인 이 구간이 정상 동작이며, 여기가 바로
      off-by-one을 눈으로 못 잡는 이유다. 반드시 discountApplied 필드로 판정할 것.

빈 장바구니  →  200   (할인 필드도 담을 줄 자체가 없다)
{ "cart": { "items": [], "totalQuantity": 0, "totalPrice": 0 } }
```

> **frontend-agent 주의 (3차):** 할인 관련 숫자를 **하나도 직접 만들지 않는다.** 취소선 칠 값은 `price`, 할인가는 `discountedUnitPrice`, 줄 합계는 `lineTotal`, 총액은 `totalPrice`를 각각 **그대로 포맷팅만 해서** 출력한다. `price * quantity`나 `price * 0.9`를 프론트 코드에 쓰면 그 순간 D12가 깨진다.

> **frontend-agent 주의 (4차 — 세 줄 요약):**
> 1. **금액을 만들지 않는다.** 결제 화면·주문 확인 화면의 모든 숫자는 서버 응답(`lineTotal`, `totalPrice`, `totalQuantity`)을 **포맷팅만** 해서 출력한다. 장바구니·결제·주문 세 화면의 총액이 항상 같아야 한다 (17.4).
> 2. **결과를 판정하지 않는다.** `MOCK_FAILURE`가 선택돼 있어도 요청을 보내고 **402를 받아서** 실패를 표시한다 (16.9). "결제 완료" 표시도 `status === "PAID"`를 근거로 그린다 (17.2).
> 3. **입력을 미리 막지 않는다.** 프론트 검증도, `required`/`pattern` 같은 HTML5 검증 속성도 쓰지 않는다. 서버 400 메시지를 그대로 보여준다 (16.18 / D25).
>
> **backend-agent 주의 (4차 — 세 줄 요약):**
> 1. **외부 PG를 호출하지 않는다.** 승인/거절은 `paymentMethod` 값 하나로 서버 안에서 결정론적으로 판정한다. `Math.random()`을 쓰면 안 된다 (18.3 / D17).
> 2. **주문 저장과 장바구니 비우기를 한 요청 안에서 끝낸다.** 그리고 `items`는 반드시 **복사본**을 저장한다 — 참조를 공유하면 장바구니를 비우는 순간 주문 내용이 함께 사라진다 (18.7).
> 3. **공용 500 에러 핸들러에 결제·주문 분기를 추가한다.** M5가 결제 API를 이름으로 지목해 예고한 재발 지점이다 (18.12).

각자 다른 스택을 고르면 통합 자체가 불가능하므로, 이번 사이클은 아래로 통일한다.

| 런타임/서버 | **Node.js 20+ / Express** | 화면 1개 + API 1개 규모에 프레임워크 학습 비용이 가장 낮고, 프론트와 언어가 같아 필드명 컨벤션(camelCase)이 자연스럽게 통일됨 |
| 데이터 | **서버 코드 내 시드 배열** (`data/products.js` 등). DB·ORM 없음 | D2 결정. 상품 목록 화면 검증에 DB가 필요 없음 |
| 프론트엔드 | **정적 HTML + CSS + 바닐라 JS** (빌드 도구/프레임워크 없음), `fetch('/api/products')`로 호출 | 화면 1개에 React/번들러는 과설계. qa-agent가 브라우저에서 바로 확인 가능 |
| 서빙 방식 | Express가 `public/`을 정적 서빙 + 같은 오리진에서 `/api/products` 제공 (**단일 서버, 단일 포트**) | CORS 설정이 아예 필요 없어져 경계면 실패 지점이 하나 줄어듦 |
| 포트 | **3000** | 고정. qa-agent가 `http://localhost:3000`으로 검증 |
| 실행 | `npm start` 한 번으로 서버 기동 | qa-agent가 기동 절차를 추측하지 않아도 됨 |

> 이 스택은 **권장이자 기본값**이다. backend-agent나 frontend-agent가 다른 스택이 꼭 필요하다고 판단하면, 임의로 바꾸지 말고 product-planner에게 먼저 문의한다 (한쪽만 바꾸면 통합이 깨진다).

## Out of scope

**4차 사이클 기준으로 갱신됨 (2026-08-10).** 아래 항목의 화면·API·모델·링크·버튼 어느 것도 구현하지 않는다.

### 🚫 4차에서 특히 강하게 금지되는 것 — 실제 결제(PG) 연동

이번 결제는 **모의 결제이며 외부 PG를 연동하지 않는다** (D16 / 최상단 제약 블록). 아래는 전부 범위 밖이다.

- **PG(결제대행사) 연동 일체** — 토스페이먼츠, 아임포트/포트원, KG이니시스, NHN KCP, 나이스페이먼츠, 카카오페이, 네이버페이, 토스페이, 페이코, Stripe, PayPal 등 **어떤 서비스도 붙이지 않는다**
- **PG SDK·스크립트 로드**, 결제창 팝업·리다이렉트, `successUrl`/`failUrl`/`returnUrl` 콜백 페이지, 웹훅 수신 엔드포인트, 결제 승인 2단계(결제창 → 승인 API)
- **실제 결제 정보 입력란** — 카드번호, 유효기간, CVC, 카드 비밀번호, 생년월일/사업자번호, 할부 개월 수, 카드사·간편결제 선택. 결제 수단 UI는 16.7의 **라디오 2개가 전부**다
- **PG 자격증명** — 가맹점 ID, 시크릿 키, 클라이언트 키, `.env` 결제 설정. 저장할 비밀값 자체가 생기지 않는다
- **결제 관련 npm 패키지 설치** (`@tosspayments/*`, `portone`, `iamport`, `stripe` 등) — `package.json`이 변경되면 범위 이탈 신호다
- 실제 승인·매입·부분 취소·환불, 영수증/현금영수증 발급, 에스크로, 정산

### 4차에서 결제와 함께 들어오지 **않는** 것

- **재고 차감 / 품절 처리 / 재고 부족으로 인한 결제 실패** — `Product`에 재고 필드를 추가하지 않는다 (D20). 결제 실패 사유는 **모의 승인 거절 하나뿐**이다 (18.4). 재고는 DB가 도입되는 사이클에 함께 넣는다
- **배송지 입력 / 우편번호 검색 / 배송비 계산 / 무료배송 기준 / 배송 상태 조회** — 결제 요청이 받는 정보는 **주문자 이름·연락처 2개뿐**이다 (D18 / 16.6)
- **주문 목록 화면 및 `GET /api/orders`(복수형)** — 단건 조회 `GET /api/orders/:orderId`만 범위에 들어왔다 (18.11). "내 주문 내역" 화면을 만들지 않는다
- **주문 취소 / 환불 요청 / 재주문 / 주문 수정** (17.13 / 18.13)
- **결제 화면·주문 확인 화면의 할인 UI** (취소선 원가, 할인 단가, 할인 안내 문구) — 할인 **표시**는 장바구니 화면 전용이며, 결제·주문 화면은 할인이 반영된 **금액만** 쓴다 (16.5 / 17.12)
- **주문 완료 알림** — 이메일·SMS·알림톡 발송, 알림 설정
- **결제 화면에서의 수량 변경·삭제** — 주문 요약은 읽기 전용이다 (16.2)
- **멱등 키(idempotency key) / 중복 결제 차단 전용 로직** — 첫 결제로 장바구니가 비워져 두 번째 요청이 409가 되는 것으로 충분하다 (18.16)
- **주문 상태 전이** (`PENDING` → `PAID` → `SHIPPED` 등) — `status`의 값은 `"PAID"` **하나뿐**이다
- **결제 비밀번호 / 본인인증 / 3DS / PCI-DSS 관련 처리** — 실제 결제 정보를 받지 않으므로 해당 사항이 없다
