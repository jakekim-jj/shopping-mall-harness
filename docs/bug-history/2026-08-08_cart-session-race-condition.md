# 장바구니 쿠키 최초 발급 경쟁 조건 (M4)

## 한 줄 요약
쿠키 없는 첫 방문자가 **동시에 여러 장바구니 관련 요청**을 보내면, 서버가 요청마다
새 `cartId`를 따로 발급해서 서로 다른 장바구니 두 개가 생기고, 브라우저는 그중
나중에 도착한 쿠키 하나만 저장한다. 결과적으로 담은 상품이 사라진 것처럼 보인다.

## 왜 생겼나 (근본 원인)
`ensureCartId()`가 "쿠키가 있으면 재사용, 없으면 새로 발급"이라는 **요청 단위** 로직으로
짜여 있었다. 요청이 순차적으로 오면 문제없지만, 같은 순간에 여러 요청이 동시에
날아오면 "쿠키가 아직 없다"는 판단이 두 번 다 참이 되어 발급이 두 번 일어난다.

## 재현 조건
- 쿠키가 아예 없는 **첫 방문**에서만 발생 (한 번 쿠키가 생기면 이후엔 재발 안 함)
- 화면이 **로드되자마자 2개 이상의 API 요청을 병렬로 쏘는 상황** (예: 배지 갱신용 요청 +
  다른 화면 데이터 요청이 동시에 나가는 경우)
- 네트워크 지연이 있는 환경일수록 발생 확률 ↑ (로컬처럼 빠른 환경에서는 창이 좁아 잘 안 보임)

## 왜 다시 터질 수 있는가 (다음 기능에서 주의할 점)
**"페이지 로드 시 여러 곳에서 각자 쿠키/세션 관련 API를 호출하는 패턴"이 새로 생기면
똑같은 문제가 재발한다.** 특히:
- 결제(체크아웃) 화면처럼, 페이지 진입과 동시에 "장바구니 재확인" + "다른 어떤 상태 확인"을
  둘 다 자동으로 호출하는 화면을 새로 만들 때
- 로그인/회원 기능을 나중에 추가해서 "세션 확인"이라는 새로운 병렬 호출이 생길 때
- 여러 컴포넌트/화면이 각자 독립적으로 "쿠키 있나 없나" 체크하며 API를 부르는 구조로
  갈 때 (지금은 이런 구조가 아니라서 우연히 피해갔을 뿐임)

## 수정 방향 (아직 미적용)
1. (권장) 정적 HTML을 서빙하는 시점에 이미 쿠키를 발급해둬서, 첫 API 요청이 오기 전에
   쿠키가 이미 존재하게 만든다 — 프론트 수정 불필요
2. (대안) 첫 배지/상태 갱신이 끝나기 전까지 사용자가 장바구니에 뭔가를 담는 액션을
   못 하게 막는다 — 프론트만 수정, 단 첫 클릭이 약간 늦어짐

## 관련 파일 (2차 사이클 시점 기준, 다음 사이클에서 위치가 바뀔 수 있음)
- `server.js` — `ensureCartId()` 관련 로직
- `public/product.js` — `loadProduct()`와 `refreshBadge()`가 동시에 실행되는 지점
