# 쇼핑몰 기획 스킬

쇼핑몰 웹사이트의 PRD를 쓸 때, 뒤에서 만들 backend-agent와 frontend-agent가 서로 다른 걸 상상하지 않도록 하는 게 이 스킬의 목적이다. 애매한 PRD는 두 사람이 각자 "말이 되는" 다른 걸 만들게 만든다.

## PRD 구조

```markdown
# {프로젝트명} PRD

## 배경
왜 이걸 만드는지 한 문단.

## 화면 목록
- 상품 목록
- 상품 상세
- 장바구니
- 결제(모의)

## 기능 요구사항
번호를 매기고, 각 항목은 "X를 하면 Y가 되어야 한다" 형태로 쓴다.
예: "1.1 상품 목록 화면에서 상품을 클릭하면 해당 상품의 상세 화면으로 이동해야 한다."
"모호하지 않게" 쓰는 게 핵심 — "잘 동작해야 한다" 같은 표현은 쓰지 않는다.

## 데이터 모델 초안
상품, 장바구니 항목의 필드명과 타입을 표로 명시.
이 필드명이 backend/frontend 양쪽에서 그대로 쓰이므로 여기서 확정한다.

## Out of scope
이번 범위에서 명시적으로 제외하는 것 (회원가입, 실제 결제 연동, 리뷰 등).
```

## 데이터 모델을 정할 때 반드시 결정해야 하는 것

이 결정을 미루면 backend-agent와 frontend-agent가 각자 다르게 가정해서 나중에 경계면 버그가 난다.

| 결정 사항 | 예시 |
|---|---|
| 필드 네이밍 컨벤션 | camelCase(`productId`) vs snake_case(`product_id`) — 하나로 통일 |
| 가격 단위 | 정수(원) vs 소수(달러) — 소수 오차 이슈 있음, 정수 권장 |
| 목록 응답이 배열인지 래핑되는지 | `[...]` 그대로 vs `{ items: [...] }` — 이것도 여기서 정하면 backend/frontend가 각자 추측 안 해도 됨 |
| 장바구니 항목 식별자 | 상품ID로 충분한지, 별도 장바구니항목ID가 필요한지 (같은 상품 여러 번 담기 지원 여부에 따라 다름) |

## 범위를 작게 유지하는 법

사용자가 "쇼핑몰 만들어줘"처럼 막연하게 요청하면, 다음 순서로 좁힌다:
1. 회원가입/로그인이 필요한지 먼저 확인 (없으면 훨씬 단순해짐)
2. 결제가 실제 PG 연동인지 모의(mock)인지 확인
3. 상품 등록/관리자 화면이 필요한지, 아니면 상품은 미리 정해진 데이터로 시작해도 되는지 확인

세 가지 다 "가장 작은 답"을 기본값으로 제안하고, 사용자가 더 원하면 그때 넓힌다.
