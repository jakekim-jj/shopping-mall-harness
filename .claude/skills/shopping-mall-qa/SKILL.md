# 쇼핑몰 QA 스킬

"API가 있다"와 "화면이 있다"를 각각 확인하는 건 약한 검증이다. 이 스킬은 **둘이 실제로 맞물리는지** 확인하는 구체적 절차를 담는다.

## 검증 절차: 상품 목록

1. `_workspace/02_backend_api-spec.md`에서 `GET /api/products` 응답 shape을 읽는다 (배열인지 `{items:[...]}` 래핑인지, 필드명)
2. frontend-agent의 실제 코드에서 이 API를 호출하는 부분을 찾아, 응답을 어떻게 꺼내 쓰는지 확인한다 (`.items`를 꺼내는지, 응답을 바로 배열로 쓰는지)
3. 둘이 다르면 → **Critical**: 화면에 상품이 아예 안 뜨거나 에러가 남
4. 상품 카드가 참조하는 필드명(`price`, `imageUrl` 등)이 백엔드 응답 필드명과 정확히 같은지 하나씩 대조

## 검증 절차: 장바구니

1. `POST /api/cart` 성공 응답에 무엇이 들어있는지 확인 (추가된 항목? 전체 장바구니? 아무것도 없음?)
2. 프론트가 장바구니에 추가한 뒤 화면을 어떻게 갱신하는지 확인 — 응답을 바로 쓰는지, 별도로 다시 GET을 하는지
3. 두 가정이 어긋나면 (예: 백엔드는 "응답에 전체 장바구니 포함"으로 짰는데 프론트는 "추가된 항목만 온다"고 가정) → 장바구니 개수가 실제와 다르게 보이는 버그로 이어짐
4. 장바구니가 비어있을 때(`GET /api/cart` → 빈 목록) 화면이 `empty-state`를 제대로 보여주는지 확인

## 검증 절차: 결제

1. `POST /api/checkout`의 성공/실패 응답을 각각 확인 — 상태 코드로 구분하는지, body의 `status` 필드로 구분하는지
2. 프론트의 결제 버튼 클릭 핸들러가 정확히 같은 기준으로 성공/실패를 판단하는지 확인
3. 실패 시 backend가 반환하는 사유(`reason` 등)를 프론트가 실제로 사용자에게 보여주는지, 아니면 무시하고 있는지 확인

## 검증 절차: 라우팅/선택자

1. frontend-agent가 만든 화면 파일 경로와, 화면 간 이동 코드(상품 클릭 → 상세 이동 등)의 실제 경로 값이 일치하는지 대조
2. `shopping-mall-frontend` 스킬에 정의된 `data-testid` 목록이 실제 화면 코드에 다 존재하는지 확인 (하나라도 빠지면 이후 테스트 자동화가 막힘)

## 리포트 작성 규칙

발견한 문제는 다음 형식으로 적는다 — "문제가 있다"로 끝내지 않는다:

```markdown
### [Critical] 상품 목록 응답 shape 불일치
- 위치: backend `/api/products` (파일:라인) vs frontend `ProductList` 컴포넌트 (파일:라인)
- 문제: 백엔드는 `{ items: [...] }`로 감싸서 반환하는데, 프론트는 응답을 바로 배열로 가정하고 `.map()` 호출
- 재현: 상품 목록 화면 접속 시 콘솔에 "items.map is not a function" 에러
- 수정 방향: 프론트에서 `response.items`를 꺼내서 매핑하도록 수정 (또는 백엔드가 배열을 그대로 반환하도록 변경 — 어느 쪽이든 한쪽만 고치고 반대편엔 알리지 않으면 재발함)
```

## 우선순위 판단 기준

- **Critical**: 화면이 아예 안 뜨거나, 사용자가 핵심 동작(담기/결제)을 못 함
- **Important**: 동작은 하지만 데이터가 부정확하게 보임 (예: 장바구니 개수가 실제와 다름)
- **Minor**: 엣지 케이스에서만 발생 (예: 상품이 정확히 0개일 때만)

## 자동화 테스트 작성 규칙

수동으로 확인한 걸 그대로 버리지 말고 `tests/e2e/*.spec.js`(Playwright)로 남긴다.

### 디렉토리/파일 구성

```
playwright.config.js       -- baseURL: http://localhost:3000, webServer로 npm start 자동 기동
tests/
  e2e/
    landing.spec.js         -- 상품 목록 화면
    product-detail.spec.js  -- 상품 상세 화면
    cart.spec.js            -- 장바구니 (담기/수량변경/삭제/비우기/할인)
  test-cases.ko.md          -- 사람이 읽는 누적 테스트 케이스 목록
```

기능 영역별로 파일을 나누는 이유: 한 파일이 계속 길어지면 다음 사이클에 어디에
테스트를 추가해야 할지 헷갈린다. 새 화면이 생기면 새 spec 파일을, 기존 화면에
기능이 추가되면 기존 spec 파일에 `test.describe()` 블록을 추가한다.

### 테스트 작성 시 반드시 지킬 것

- **`data-testid` 선택자만 쓴다.** CSS 클래스나 텍스트로 요소를 찾지 않는다 (디자인이
  바뀌면 깨짐). `docs/bug-history/`의 M2 교훈 — 요소가 "존재하는지"와 "지금 보이는지"는
  다르다. 빈/에러 상태 테스트에서 다른 요소가 안 보이는 걸 확인할 땐 `toBeHidden()`을,
  요소 자체가 DOM에 없어야 하는 경우(예: 할인 미적용 줄의 할인 표시)엔 `toHaveCount(0)`을
  정확히 구분해서 쓴다.
- **경계값은 명시적으로 테스트한다.** "약 10개 담으면 할인"이 아니라 정확히 9개(할인 안 됨)와
  10개(할인 됨)를 각각 테스트한다. 금액이 우연히 같아 보이는 경우, 최종 금액이 아니라
  판단 근거가 되는 필드(예: `discountApplied`)나 UI 요소의 존재 여부로 단언한다.
- **서버를 매번 새로 시작하지 않는다.** 이 프로젝트는 장바구니가 쿠키 기반 세션이므로,
  각 테스트가 고유한 상품 조합/브라우저 컨텍스트를 써서 서로 간섭하지 않게 한다
  (완전히 새 컨텍스트를 만들면 새 세션이 되어 자연히 격리된다).
- **spec 파일(=화면/PRD 단위) 하나당 브라우저 컨텍스트(창)를 하나만 공유한다.**
  Playwright 기본값은 테스트마다 새 컨텍스트를 여는 것인데, `--headed`로 사람이 직접
  지켜볼 때 파일 하나에 테스트가 여러 개면 창이 계속 깜빡여서 보기 불편하다. 파일
  최상단에 파일 전체가 공유할 `page`(또는 `context`)를 `test.beforeAll`에서 한 번만
  만들고, 그 파일의 모든 테스트가 이를 재사용하도록 구성한다. **단, 이렇게 창을
  공유해도 테스트 간 데이터가 섞이면 안 된다** — 각 테스트는 자기가 다루는 상품을
  명확히 정하거나(예: 이 테스트는 p1만, 저 테스트는 p2만 사용), 테스트 시작 시
  `DELETE /api/cart`로 장바구니를 비우고 시작하는 방식으로 격리한다. "여러 브라우저가
  서로 독립적인지"(PRD 8.5류) 자체를 검증하는 테스트는 이 규칙의 예외로, 그 테스트
  안에서 별도 컨텍스트를 추가로 열어도 된다.
- **작성 후 반드시 `npx playwright test`로 실행해서 통과를 확인한다.** 컨텍스트를
  공유하도록 바꾼 뒤에는 `--headed --workers=1`로도 한 번 실행해서, 창이 파일당
  1개만 뜨는지 직접 눈으로 확인한다.

### `tests/test-cases.ko.md` 작성 규칙

- 처음 보는 사람(비개발자 포함)도 이해할 수 있는 문장으로 쓴다 — "PATCH 요청 시
  quantity가 절대값으로 처리됨"이 아니라 "장바구니에서 수량을 3으로 바꾸면 3으로
  저장되고, 이전 값에 3을 더하는 식으로 처리되지 않는다"처럼 쓴다.
- 함수/테스트 이름은 참고용으로만 괄호에 병기한다.
- PRD 요구사항 번호와 매핑해서 커버리지를 추적할 수 있게 한다.
- 사이클별로 섹션을 나누고, 기존 섹션은 지우지 않고 이어서 추가한다.
